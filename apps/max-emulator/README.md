# Эмулятор MAX v0 — S1-05

Локальный HTTP-сервис для MAX-адаптера Backend на `maxapi 1.2.3`.
Создаёт входящие сообщения с текстом и тестовым фото, выдаёт их через polling
и сохраняет текстовые ответы клиента. Форматы основаны на примерах S1-04
из [packages/contracts/max](../../packages/contracts/max/README.md).
Содержание ответов и состояние заявок определяет Backend.

## Запуск

Из корня репозитория:

```bash
uv sync --locked
uv run uvicorn max_emulator:create_app --factory --app-dir apps/max-emulator --host 127.0.0.1 --port 8081
```

Один процесс, данные в памяти. Перезапуск очищает сообщения, ответы и маркеры.
По умолчанию используется синтетический токен `local-emulator-token`.
Для смены токена задайте переменную `MAX_EMULATOR_TOKEN` перед запуском;
настоящий токен MAX эмулятору не нужен. `.env` автоматически не загружается.
Интерактивное описание методов доступно на `http://localhost:8081/docs`;
заголовок `authorization` указывается при выполнении запроса.

## Отправка тестовых сообщений

Текст от синтетического пользователя:

```bash
export MAX_EMULATOR_TOKEN=local-emulator-token
curl -sS http://localhost:8081/__test__/messages \
  -H "Authorization: $MAX_EMULATOR_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"user_id":2001,"text":"/start"}'
```

Фото от того же пользователя:

```bash
curl -sS http://localhost:8081/__test__/messages \
  -H "Authorization: $MAX_EMULATOR_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"user_id":2001,"photo":true}'
```

Можно передать `text` вместе с `photo`. Служебный метод возвращает созданное
событие и маркер после него. В v0 `chat_id` диалога совпадает с `user_id`;
допускаются синтетические ID больше 1001. ID бота — 1001.
Вложения содержат `type=image`, `photo_id`, синтетический `token` и URL файла
на самом эмуляторе. `photo=true` использует одно
[сгенерированное фото растения](assets/README.md), доступное по
`/media/seedling.png` без авторизации. URL строится из адреса запроса добавления
сообщения: этот адрес должен быть доступен процессу, который скачивает фото.
Это позволяет проверить передачу настоящих байтов. Загрузка произвольных фото,
upload и интеграция с fetcher остаются дальнейшей работой S2-12.

Просмотр ответов, которые клиент отправил через `POST /messages`:

```bash
curl -sS http://localhost:8081/__test__/outgoing \
  -H "Authorization: $MAX_EMULATOR_TOKEN"
```

Без подключённого клиента список ответов остаётся пустым.
Пути `/__test__/...` — собственный API управления эмулятором, не методы MAX.

## Контракт v0

| Метод | Поведение |
| --- | --- |
| `GET /me` | Синтетическая информация о боте для запуска SDK |
| `GET /subscriptions` | Пустой список для штатной проверки SDK перед polling |
| `GET /updates` | События `message_created` с текстом и/или фото |
| `POST /messages?chat_id=...` или `?user_id=...` | Текстовый ответ существующему тестовому пользователю; результат `{"message": ...}` |
| `POST /__test__/messages` | Добавление входящего сообщения |
| `GET /__test__/outgoing` | Ответы клиента в порядке отправки |
| `GET /media/seedling.png` | Синтетическая PNG-фикстура без авторизации |

Методы API требуют заголовок `Authorization: <тестовый токен>`;
раздача `/media/` доступна без него. Неверный или
отсутствующий токен даёт 401. Невалидные тела и параметры дают 422.
Для `/messages` нужен ровно один адресат (иначе 400), созданный входящим
сообщением (иначе 404). Поддерживаются `text`, пустой `attachments` и `notify`;
разметка, исходящие вложения и другие поля пока отклоняются.
Ошибки имеют формат FastAPI `detail`; точные ошибки MAX в v0 не воспроизводятся.

`GET /updates` поддерживает `limit=1..1000` (по умолчанию 100),
`timeout=0..90` секунд (по умолчанию 30), `types` через запятую и неотрицательный
целочисленный `marker`. Без маркера возвращается только последнее событие.
Для чтения всей локальной истории передайте `marker=0`.
Далее передавайте маркер предыдущего ответа. Маркер указывает на следующую
позицию в журнале и не зависит от `message.body.seq`.
Повторный запрос с тем же маркером сохраняет ID и содержание событий.
Фильтр пропускает неподходящие типы с продвижением маркера; пустая очередь
ожидает подходящее событие до таймаута. Маркер за пределами журнала даёт 400.
После перезапуска эмулятора сохранённый клиентом маркер нужно сбросить
вместе с тестовыми данными клиента. TTL, rate limit и удаление прочитанных
событий не моделируются.
Параметры и старт без маркера — по [контракту MAX](https://dev.max.ru/docs-api/methods/GET/updates).

## Подключение maxapi и передача Dev2

Настройки будущего адаптера Backend при запуске обоих процессов на хосте:

```dotenv
MAX_MODE=mock
MAX_API_BASE_URL=http://localhost:8081
```

На стороне SDK подключение выглядит так:

```python
from maxapi import Bot

bot = Bot(token="local-emulator-token", auto_requests=False)
bot.set_api_url("http://localhost:8081")
```

`auto_requests=False` отключает дополнительную загрузку чата: `/chats/{id}`
в v0 отсутствует. Отправитель, адресат и вложения доступны в самом событии.
Пример показывает настройки SDK, а не готовый Backend-адаптер.
В mock-режиме Dev2 должен выбрать синтетический токен вместо настоящего
`MAX_BOT_TOKEN`, направить SDK на `MAX_API_BASE_URL` и обеспечить обработку
и сохранение `marker` согласно [contracts.md](../../docs/contracts.md).
Совместимость с фактическим адаптером требует проверки после S1-06.

## Проверки и статус

```bash
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
```

Тесты проверяют маркеры и повторное чтение, фильтры, long polling, авторизацию,
валидацию и основные формы записанных ответов. Интеграционный тест поднимает
Uvicorn на свободном порту `127.0.0.1` и проверяет через настоящий `maxapi`
стартовые запросы, получение текста/фото, скачивание PNG по URL события без
авторизации с проверкой байтов, диспетчеризацию и отправку ответов.
Тестовый обработчик нужен только для проверки SDK и не реализует поведение бота.

FastAPI 0.162.0 и Uvicorn 0.54.0 выбраны из стабильных релизов PyPI на момент
реализации; оба заявляют Python 3.14. Pydantic 2.14.1 используется для входных
моделей. `maxapi` закреплён на 1.2.3, версии исследования S1-04, и вместе
с HTTPX находится в dev-зависимостях. Прямые зависимости закреплены
в `pyproject.toml`, полный набор — в `uv.lock`.

**S1-05 не закрыта:** Backend S1-06 пока отсутствует. Не проверены его
`MAX_MODE=mock`, `/start`, создание заявки из фото, дедупликация и реальный
ответ Backend. Проверка SDK не заменяет критерий приёмки задачи.
Compose относится к S1-03; интеграция с fetcher, upload и канал — к S2-12.
