# Backend: справочник по коду

Этот файл помогает вспомнить, где находится нужная логика и как части Backend
работают вместе. Описание сверено с кодом 16 ноября 2026 года. При изменении
Backend обновляем соответствующие разделы этого справочника вместе с кодом.

Подробные команды настройки и запуска: [README](README.md).
Состояние задачи и ограничения: [S1-06](../../docs/results/s1-06-progress.md).
Контейнерный запуск существующих точек входа: корневой
[compose.yaml](../../compose.yaml), цели `backend`/`max-emulator` в
[Dockerfile](../../Dockerfile) и [инструкция](../../docs/operations.md#локальный-compose-s1-03).
Сервис `migrate` применяет миграции до `backend` и `bot`; Compose передаёт
внутренний `BACKEND_DATABASE_URL` из `POSTGRES_*`, не читая его из `.env` целиком.

## 1. Общая картина

Backend получает сообщения MAX, решает, что с ними сделать, сохраняет результат
в PostgreSQL и отправляет ответ. Сейчас он работает с локальным эмулятором.

Есть три отдельных способа запуска:

| Точка входа | Что запускает | Когда нужна |
| --- | --- | --- |
| `backend:create_app` через Uvicorn | HTTP-сервер FastAPI | Сейчас только проверка `/health/live` и Swagger `/docs` |
| [run_bot.py](run_bot.py) | Простой бот без БД | Проверить связь с эмулятором и ответы |
| [run_inbox_bot.py](run_inbox_bot.py) | Бот с PostgreSQL | Сохранять историю обработки, согласия и заявки |

Запуск HTTP-сервера сам по себе не запускает бота. Для получения сообщений
HTTP-сервер Backend сейчас не требуется. Два варианта бота одновременно
на одном источнике запускать не следует.

Без `BACKEND_CAMPAIGN_ID` бот с PostgreSQL сохраняет входящие события и отвечает
простыми подсказками. С настроенной кампанией включается создание заявок
и регистрация согласия.

## 3. HTTP-приложение: `backend/__init__.py`

- `HealthResponse` — модель ответа с полем `status`. Pydantic описывает форму данных.
- `create_app()` — создаёт и возвращает объект `FastAPI`, регистрирует маршруты.
- Вложенная `liveness()` — обработчик `GET /health/live`, возвращает `{"status":"ok"}`.

Эта проверка показывает, что HTTP-процесс способен ответить. Она не проверяет
подключение к БД. Входа модераторов и методов панели здесь пока нет.

Запись `create_app() -> FastAPI` означает: функция должна вернуть объект
типа `FastAPI`. Стрелка — аннотация типа результата, а не операция возврата.
Сам возврат выполняет `return`.

## 4. База данных: `backend/database.py`

`database_engine()` читает `BACKEND_DATABASE_URL` и создаёт SQLAlchemy `Engine`.
Это объект для управления подключениями к БД. Функция допускает PostgreSQL;
она не создаёт саму базу и таблицы. `pool_pre_ping=True` помогает проверять
живость подключений, `hide_parameters=True` скрывает параметры SQL в сообщениях
SQLAlchemy об ошибках.

`Base` — общий родитель классов таблиц. Через него SQLAlchemy собирает описание
структуры БД (`Base.metadata`). Остальные классы описывают строки таблиц:

| Класс | Таблица | Что хранится |
| --- | --- | --- |
| `PollingCursor` | `max_polling_cursors` | До какой позиции прочитана история конкретного источника и бота |
| `InboxEvent` | `max_inbox_events` | Принятое сообщение, выбранный ответ и состояние его отправки |
| `User` | `users` | Внутренний UUID пользователя, связь с MAX-ID, случайный `author_ref` |
| `Campaign` | `campaigns` | Кампания и её текущая версия правил |
| `CampaignRules` | `campaign_rules` | Текст каждой версии правил кампании |
| `ConsentPrompt` | `consent_prompts` | Связь ответа с правилами, пользователя, кампании и версии правил |
| `Consent` | `consents` | Кто, в какой кампании, когда и с какой версией правил согласился |
| `Submission` | `submissions` | Заявка, автор, кампания, согласие, статус, версия и даты |
| `AuditEvent` | `audit_events` | История создания заявки и изменения её статуса |

`ConsentPrompt` сам по себе ещё не доказывает отправку правил: дополнительно
проверяется состояние `sent` связанного события inbox.

Ограничения таблиц защищают данные: уникальные ключи запрещают повторы,
внешние ключи связывают записи, проверки ограничивают допустимые значения.
Например, согласие заявки должно принадлежать её пользователю и кампании.
Имя пользователя не сохраняется; MAX-ID остаётся внутренним полем БД.

Описание класса таблицы не изменяет существующую БД автоматически.
При изменении схемы нужны и правка модели, и новая миграция.

## 5. Простой бот: `backend/polling.py` и `backend/replies.py`

Это вариант для проверки связи. Он не создаёт заявки и не сохраняет согласия.

### `polling.py`

- `create_mock_bot()` — создаёт клиент библиотеки `maxapi`. Проверяет
  `MAX_MODE`, адрес эмулятора и использует `MAX_EMULATOR_TOKEN`. Разрешает
  только локальные HTTP-адреса и имя `max-emulator`. Реальные режимы MAX пока
  отклоняются. Автоматические повторы сетевых запросов SDK отключены.
- `MockPollingBot.__init__()` — сохраняет клиент и создаёт коллекцию ключей
  сообщений, на которые уже ответили в этом процессе.
- `MockPollingBot.poll_once(marker, timeout=20)` — один проход: запрашивает
  события, проверяет их, пропускает неподдерживаемые сообщения и повторы,
  выбирает ответы, отправляет их и возвращает следующий marker.
- `run()` — получает сведения о боте, начинает с marker `0` и повторяет
  `poll_once()` в цикле. При выходе закрывает сетевую сессию.
- `main()` — запускает асинхронную `run()` через `asyncio.run()`, обрабатывает
  Ctrl+C и сообщает об ошибке. При ошибке процесс завершается с кодом `1`.

Дедупликация здесь хранит последние 1000 ключей `(chat_id, mid)` в памяти.
После перезапуска эта память и marker теряются: возможен повторный ответ
на старую историю. Разные сообщения с одинаковым текстом считаются разными.

### `replies.py`

`choose_reply(text, has_photo=...)` выбирает строку ответа для `/start`, `/help`,
фото или другого текста. Функция не обращается к сети и БД.
В режиме с кампанией окончательный ответ выбирает `submissions.process_message()`.

### `run_bot.py`

Маленькая точка входа, вызывающая `polling.main()` при запуске файла как программы.
Проверка `if __name__ == "__main__"` позволяет импортировать файл без запуска бота.

## 6. Приём и хранение событий: `backend/inbox.py`

Inbox — наша таблица принятых событий. Она позволяет узнать, обрабатывали ли
мы сообщение раньше, и сохранить результат до отправки ответа.

### Объекты данных

- `ReceivedMessage` — подготовленные данные входящего сообщения: ID, чат,
  текст, признак кандидата image/file, предварительный ответ, ID отправителя
  и `media_count` — число вложений image/file в текущем событии.
- `PendingReply` — данные для отправки: ID записи inbox, чат и текст ответа.
- `normalize_message(raw_event)` — проверяет событие через модель SDK
  `MessageCreated` и превращает его в `ReceivedMessage`. Отвечать можно человеку
  в личном диалоге. URL и токены вложений не сохраняются. Событие без ID
  сообщения вызывает ошибку, чтобы история не была молча пропущена.
  Один image/file — кандидат на изображение. При нескольких таких вложениях
  формируется просьба прислать по одному; заявки и согласия не создаются.
  `media_count` нужен до сохранения результата, отдельной колонки для него нет.

Оба класса данных используют `@dataclass(frozen=True)`: Python создаёт
конструктор, а обычное присваивание их полям после создания запрещено.

### Методы `InboxStore`

| Метод | Что делает |
| --- | --- |
| `__init__()` | Запоминает Engine, источник, ID бота и необязательную кампанию; проверяет длину имени источника |
| `marker()` | Создаёт запись позиции с нулём, если её ещё нет, и возвращает сохранённую позицию |
| `save_batch(marker, next_marker, messages)` | Сохраняет порцию сообщений, применяет бизнес-логику новых событий и передвигает marker одной транзакцией |
| `claim_reply()` | Берёт один `pending`-ответ, переводит его в `sending` и возвращает данные отправки; если ответов нет, возвращает `None` |
| `finish_reply(event_id, state)` | Переводит выбранную запись из `sending` в `sent` или `unknown` |
| `unresolved_count()` | Считает записи в `sending` и `unknown` для предупреждения при запуске |

Подробно про `save_batch()`:

1. Запрещает уменьшение marker.
2. Блокирует строку текущей позиции и проверяет, что другой процесс её не изменил.
3. Вставляет события с уникальным ключом
   `(source_id, bot_id, update_type, message_id)`.
4. Если такое событие уже существует, пропускает его бизнес-обработку.
5. Для нового поддерживаемого сообщения при настроенной кампании вызывает
   `process_message()` и сохраняет полученный ответ. Группа вложений
   сохраняет заранее выбранный ответ без бизнес-обработки.
6. Сохраняет следующий marker. Успешный выход из `session.begin()` коммитит
   всё вместе; ошибка откатывает всю порцию.

`claim_reply()` использует блокировку строки с `skip_locked=True`: занятые
строки пропускаются. Это отдельная транзакция, которая завершается до
сетевой отправки. Методы этого файла сами HTTP-запросы не выполняют.

### Состояния отправки ответа

| Состояние inbox | Значение |
| --- | --- |
| `pending` | Ответ сохранён, попытка отправки ещё не началась |
| `sending` | Попытка зафиксирована перед сетевым запросом |
| `sent` | SDK подтвердил отправку, результат записан в БД |
| `unknown` | При отправке произошла ошибка, результат не считается известным |
| `ignored` | Событие не требует ответа |

После перезапуска `pending` продолжит отправляться. `sending` и `unknown`
автоматически не повторяются: ответ мог уже уйти. Пока такие случаи разбираем
вручную, сверяя inbox и исходящие сообщения эмулятора.

## 7. Основной цикл с БД: `backend/durable_polling.py`

Этот файл соединяет сеть и хранилище. SQL-операции выполняются через
`asyncio.to_thread()`, потому что используемый драйвер БД синхронный: его
ожидание переносится в поток и не занимает асинхронный цикл событий.

- `DurablePollingBot.__init__()` — сохраняет клиент MAX и `InboxStore`.
- `deliver_pending()` — забирает ответы через `claim_reply()` и отправляет.
  После подтверждения SDK записывает `sent`. При исключении записывает
  `unknown` и передаёт ошибку выше. Аварийная остановка может оставить `sending`.
- `poll_once()` — сначала отправляет ранее сохранённые `pending`, читает
  marker из БД, получает порцию MAX, нормализует сообщения, сохраняет порцию
  и отправляет новые ответы. Возвращает следующий marker.
- `run()` — создаёт Engine и клиент, читает UUID кампании, проверяет её наличие,
  узнаёт ID бота, создаёт хранилище и запускает цикл `poll_once()`. При выходе
  закрывает клиент и освобождает подключения Engine.
- Вложенная `check_campaign()` — проверяет наличие настроенной кампании в БД.
  Не создаёт её автоматически.
- `main()` — запускает `run()`, обрабатывает остановку и выводит безопасное
  сообщение об ошибке без параметров подключения и содержимого сообщений.

### `run_inbox_bot.py`

Точка входа, вызывающая `durable_polling.main()`.

### Полный путь сообщения

```text
Эмулятор → get_updates(marker) → normalize_message()
    → InboxStore.save_batch()
        → новое событие inbox
        → process_message(): пользователь / согласие / заявка / аудит
        → текст ответа и следующий marker
        → общий COMMIT
    → claim_reply(): pending → sending, COMMIT
    → send_message() через сеть
    → finish_reply(): sent либо unknown, COMMIT
```

Общая транзакция защищает результат обработки входящего сообщения.
Сетевой запрос отправки не входит в эту транзакцию. Поэтому гарантии
«ответ обязательно доставится ровно один раз» сейчас нет.

## 8. Правила работы с заявками: `backend/submissions.py`

Эти функции работают с переданной `Session`. Они не отправляют сообщения
по сети и не делают самостоятельный `commit()`: транзакцией управляет вызывающий код.

### `register_campaign(session, slug, version, text)`

Создаёт кампанию или находит существующую по короткому имени `slug`, добавляет
версию правил и делает её текущей. Возвращает UUID кампании. Проверяет длину
полей: slug по шаблону `[a-z0-9][a-z0-9-]{0,63}`, версия до 64 без пробельных символов, непустой текст
до 2400 символов. Другой текст под уже существующей версией запрещён;
нужно указать новую версию. Повтор тех же параметров сохраняет ID кампании.

### `record_audit(session, submission, event_id, previous, user_id, reason)`

Добавляет запись истории: заявка, порядковый номер, исходное событие,
старый и новый статусы, время, причина и пользователь. Порядковый номер
равен текущей `version` заявки. Сейчас причины — `PHOTO_RECEIVED`
и `CONSENT_ACCEPTED`, участник изменения — `user`.

### `process_message(session, event, campaign_id)`

Находит кампанию и текущие правила, создаёт или находит пользователя,
ищет его согласие с текущей версией. Возвращает текст будущего ответа.

| Вход | Действия |
| --- | --- |
| Сообщение с фото | Создаёт заявку: `validating`, если согласие есть, иначе `awaiting_consent`; записывает аудит |
| `/start` | Возвращает приветствие и текущие правила |
| `/help` | Возвращает подсказку по командам |
| `/agree ВЕРСИЯ` | Проверяет версию и ранее подтверждённую отправку правил; сохраняет согласие и переводит ожидающие заявки в `validating` |
| `/agree` | Аналогично, для текущей версии правил |
| Другой текст | Предлагает `/start` и `/help` |

Вложенная `prompt()` сохраняет `ConsentPrompt` и формирует текст правил
с командой согласия. Для нового согласия нужна ранее отправленная версия
правил: связанный ответ должен иметь состояние `sent`. Два сообщения
`/start` и `/agree` в одной ещё не отвеченной порции не дают согласие автоматически.

Один `file` также считается кандидатом; его формат пока не проверяется.
Несколько вложений отсеиваются в inbox до вызова этой функции.
Фото проверяется раньше команды: подпись `/agree` на фото не считается согласием.
При согласии все ожидающие заявки пользователя в этой кампании получают ссылку
на согласие, статус `validating`, увеличенную `version`, новую дату и аудит.
Новая заявка начинает с `version=1`.

Согласие относится к сочетанию пользователь + кампания + версия правил.
После смены правил новые фото снова требуют согласия, старые заявки сохраняют
прежнюю ссылку. Эти правила приняты Dev3/Dev4 в PR #12; PR влит 14 ноября 2026.

`validating` сейчас означает сохранённое состояние заявки: скачивание файла
и реальная CV-проверка автоматически не запускаются.

## 9. Административные и служебные файлы

### `manage.py`

`main()` разбирает параметры `--slug`, `--rules-version`, `--rules-file`,
читает текст правил, открывает транзакцию и вызывает `register_campaign()`.
Печатает `BACKEND_CAMPAIGN_ID=...`, затем освобождает Engine.
Бота и HTTP-сервер эта команда не запускает.

### `demo-rules.txt`

Демонстрационный текст для локального стенда. Это не утверждённые правила
реальной кампании.

### `alembic.ini`

Настройки Alembic: где искать миграции и откуда импортировать Backend.
Параметры подключения берутся из окружения через `database_engine()`.

### `migrations/env.py`

Связывает Alembic, Engine и описание таблиц. `migrate(connection)` настраивает
контекст и выполняет миграции в транзакции. На уровне модуля выбирается
подключение: переданное извне (используется тестами) или созданное через Engine.

### `migrations/versions/0001_max_inbox.py`

- `upgrade()` создаёт первоначальные таблицы inbox и marker с ограничениями.
- `downgrade()` удаляет эти таблицы.

### `migrations/versions/0002_submissions.py`

- `upgrade()` добавляет отправителя в inbox и семь таблиц для пользователей,
  кампаний, правил, предъявления правил, согласий, заявок и аудита.
- `downgrade()` удаляет добавленные таблицы и поле, возвращая схему к `0001`.

Миграция — сохранённое изменение структуры БД. Alembic помнит применённую
версию в `alembic_version`. `upgrade head` применяет только недостающие шаги;
при каждом запуске БД заново не создаётся. Удаление таблиц через `downgrade`
также удаляет их данные. Уже применённые миграции не переписываем для новых изменений.

## 10. Какие идентификаторы не путать

| Значение | Для чего |
| --- | --- |
| `marker` | Позиция чтения истории MAX; не ID последнего сообщения |
| `message.body.mid` / `message_id` | ID сообщения MAX, нужен для отсечения повторной доставки |
| `chat_id` | Куда отправлять ответ |
| MAX `user_id` / `sender_id` | Кто отправил сообщение в MAX |
| `bot_id` | Какому боту принадлежит история |
| `source_id` | Какую историю эмулятора мы читаем |
| `User.id` | Внутренний UUID пользователя в нашей БД |
| `author_ref` | Отдельное случайное обозначение автора для внешних контрактов |
| `Submission.id` | UUID заявки |
| `Submission.version` | Версия состояния заявки, увеличивается при изменении |

Обычный перезапуск бота сохраняет `MAX_SOURCE_ID`. После сброса эмулятора
история и ID начинаются заново: бота останавливаем и выбираем новый источник.
Сравнение текста или фотографии — другая задача: два новых сообщения
с одинаковым содержимым не являются повторной доставкой одного события.

## 12. Короткий словарь конструкций

| Конструкция | Простыми словами |
| --- | --- |
| `Engine` | Управляет подключениями к БД |
| `Session` | Выполняет операции с БД и отслеживает изменения объектов |
| `with Session(...)` | Открывает сессию и закрывает её при выходе, в том числе при ошибке |
| `with session.begin()` | На успехе коммитит транзакцию, при ошибке откатывает |
| `session.add(obj)` | Добавляет объект для сохранения |
| `session.flush()` | Отправляет накопленные изменения в БД внутри текущей транзакции; ещё не делает их окончательными |
| `commit()` / `rollback()` | Зафиксировать / отменить изменения транзакции |
| `select(Model)` | Построить запрос чтения |
| `session.execute(...)` | Выполнить запрос и получить объект результата |
| `.scalar_one()` | Получить единственное значение одной строки; ошибка, если строк ноль или больше одной |
| `.scalar_one_or_none()` | Аналогично, но отсутствие строки возвращает `None` |
| `.scalars().all()` | Получить список первых элементов строк результата; для `select(Model)` это объекты модели |
| `.with_for_update()` | Заблокировать выбранные строки от конкурирующих изменений до завершения транзакции |
| `.on_conflict_do_nothing()` | При конфликте уникальности пропустить вставку |
| `async def` / `await` | Асинхронная функция / ожидание результата с возможностью выполнения других асинхронных задач |
| `asyncio.to_thread(fn, ...)` | Выполнить обычную блокирующую функцию в отдельном потоке |
| `while reply := ...` | Присвоить результат переменной и продолжать цикл, пока он истинный; `None` завершает цикл |
| `try ... finally` | Выполнить очистку ресурсов при выходе как с успехом, так и с ошибкой |

`sqlite3.Cursor.fetchone()` из учебного примера возвращает следующую строку
или `None`; `fetchall()` — список оставшихся строк, включая пустой `[]`.
SQLAlchemy использует собственный объект результата и перечисленные выше методы.

## S1-17: доставка через outbox и RabbitMQ (26 ноября)

- `ReplyOutbox` в database.py — одна исходящая запись на событие inbox;
  создаётся в той же транзакции, что заявка, аудит, ответ и marker.
- `0003_reply_outbox.py` создаёт таблицу и переносит старые pending-ответы.
- `delivery.queue_name()` разделяет очереди источников/ботов по хешу.
- `delivery.connect()` открывает ограниченное по времени AMQP-соединение,
  объявляет durable-очередь и включает publisher confirms.
- `dispatch_one()` блокирует одну неопубликованную запись, публикует только
  внутренний UUID (без текста и MAX-ID), persistent + mandatory. Метка публикации
  сохраняется после confirm. Авария между confirm и commit допускает повтор того же ID.
- `parse_notification()` проверяет размер, форму JSON и UUID.
- `notify()` берёт конкретный pending-ответ через claim_reply(event_id),
  фиксирует sending перед MAX-запросом, затем sent/unknown. Повторное
  сообщение очереди для sending/unknown/sent не вызывает повторной отправки.
- `delivery.main()` запускает роль dispatcher либо notifier. ACK — после
  записи результата в БД. Ошибка БД оставляет сообщение неподтверждённым;
  процесс завершается и Compose перезапускает его. Невалидные сообщения
  явно отклоняются без бесконечного requeue; содержимое не логируется.
- `run_delivery.py` — точка запуска этих двух процессов.
- `DurablePollingBot(..., broker_delivery=True)` только принимает и сохраняет
  события; direct оставлен для учебного запуска и совместимости.

Compose включает broker-режим. Не запускайте direct-получатель параллельно
с notifier для одного источника. Sending/unknown требуют ручной сверки,
а не слепого повтора. После сброса эмулятора остановите все три процесса
и смените MAX_SOURCE_ID согласованно. Временные лимиты RabbitMQ не заменяют
MAX rate limiting: общий лимитер — S2-05.
