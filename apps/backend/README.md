# Backend — начальный каркас Dev2

Реализованы проверка работоспособности HTTP-процесса и отдельный polling-процесс
для эмулятора: ответы на `/start`, `/help`, текст и фото без скачивания файлов.
Режим с PostgreSQL поддерживает inbox, маркер, пользователей, кампании,
версионированные согласия, заявки и аудит. Приём заявок включается только
после явной настройки кампании. Решения S1-07 требуют командного ревью;
S1-06 не отмечается закрытой до этой приёмки. Аккаунты панели, сессии,
outbox/RabbitMQ и методы панели ещё не реализованы (S1-17/S1-18).

Из корня репозитория после `uv sync --locked`:

```bash
uv run uvicorn backend:create_app --factory --app-dir apps/backend --host 127.0.0.1 --port 8000
```

Если uv не установлен, но зависимости уже есть в `.venv`:

```bash
.venv/bin/uvicorn backend:create_app --factory --app-dir apps/backend --host 127.0.0.1 --port 8000
```

`GET http://127.0.0.1:8000/health/live` возвращает `{"status":"ok"}`.
Это liveness, не проверка готовности БД/брокера. Swagger: `/docs`.
Активация окружения в fish: `source .venv/bin/activate.fish`.

## Локальный бот без БД

Сначала запустите эмулятор в первом терминале:

```bash
.venv/bin/uvicorn max_emulator:create_app --factory --app-dir apps/max-emulator --host 127.0.0.1 --port 8081
```

Во втором терминале запустите Backend-процесс бота из корня репозитория:

```bash
.venv/bin/python apps/backend/run_bot.py
```

HTTP-сервер Backend на 8000 для этого не нужен. Это два независимых процесса
одного приложения: HTTP API и получение событий MAX. Остановка бота — Ctrl+C.

По умолчанию: `MAX_MODE=mock`, `MAX_API_BASE_URL=http://127.0.0.1:8081`,
`MAX_EMULATOR_TOKEN=local-emulator-token`. `.env` автоматически не читается;
учитываются экспортированные переменные окружения. Если они уже заданы,
для fish можно запустить с явными значениями:

```fish
env MAX_MODE=mock MAX_API_BASE_URL=http://127.0.0.1:8081 MAX_EMULATOR_TOKEN=local-emulator-token .venv/bin/python apps/backend/run_bot.py
```

Настоящий `MAX_BOT_TOKEN` не используется. Допустимы только HTTP-адреса
localhost, 127.0.0.1, ::1 и max-emulator (для будущего Compose), без пути.
Режимы реального polling/webhook пока отклоняются.

В третьем терминале добавьте тестовое сообщение:

```bash
export MAX_EMULATOR_TOKEN=local-emulator-token
curl -sS http://127.0.0.1:8081/__test__/messages \
  -H "Authorization: $MAX_EMULATOR_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"user_id":2001,"text":"/start"}'
```

Для помощи замените текст на `/help`; для фото используйте
`{"user_id":2001,"photo":true}`. Посмотреть ответы:

```bash
curl -sS http://127.0.0.1:8081/__test__/outgoing \
  -H "Authorization: $MAX_EMULATOR_TOKEN"
```

Бот отвечает только в личных диалогах, пропускает сообщения ботов.
В режиме проверки связи без кампании `/agree` не регистрирует согласие:
получает обычную подсказку. Сценарий с кампанией описан ниже.
URL фото не открываются, персональные данные и текст сообщений не логируются.

Маркер начинается с 0 и живёт в памяти. Повторы последних 1000 успешно
отвеченных сообщений отсеиваются по `(chat_id, mid)` в текущем процессе;
это ограниченная локальная защита, не долговечный inbox. Разные сообщения
с одинаковым текстом получают отдельные ответы. После перезапуска бота
старая история обрабатывается повторно. Для чистого демо остановите оба
процесса, перезапустите эмулятор, затем бота.

При ошибке приёма или отправки процесс завершается с кодом 1; сетевые повторы
SDK отключены. Неизвестный исход отправки пока не сохраняется — это требует
БД/outbox. Не запускайте несколько получателей на одном эмуляторе.
Правила ответов находятся в `backend/replies.py`, работа SDK — в
`backend/polling.py`. Webhook впоследствии сможет использовать те же правила,
но потребует отдельного надёжного приёма событий и проверки секрета.

## Режим с PostgreSQL: долговечный inbox

Старый `run_bot.py` остаётся проверкой связи без БД. `run_inbox_bot.py`
без BACKEND_CAMPAIGN_ID также работает как проверка связи, но сохраняет inbox.
Не запускайте два получателя одновременно на одном эмуляторе.

Установите зависимости через `uv sync --locked`. Подключение задаётся
экспортированной переменной `BACKEND_DATABASE_URL` вида
`postgresql+psycopg://USER:PASSWORD@HOST:PORT/DATABASE`. Заполненное значение
храните локально, не добавляйте в Git. База должна существовать;
миграции создают только таблицы внутри неё. SQLite для этого режима не поддерживается.

Для отдельной локальной БД можно выполнить в fish (Docker должен работать):

```fish
set -gx POSTGRES_PASSWORD (openssl rand -hex 24)
docker run -d --name vision-shield-local-pg --env POSTGRES_PASSWORD --env POSTGRES_DB=vision_shield -p 127.0.0.1:5433:5432 -v vision-shield-local-pg:/var/lib/postgresql postgres:18-alpine@sha256:1018733457011bf88d81db98cf43aac6d5150afc18787dbe204771fedf80ff95
set -gx BACKEND_DATABASE_URL "postgresql+psycopg://postgres:$POSTGRES_PASSWORD@127.0.0.1:5433/vision_shield"
docker exec vision-shield-local-pg pg_isready -U postgres -d vision_shield
```

Дождитесь `accepting connections`, затем примените миграцию:

```bash
.venv/bin/alembic -c apps/backend/alembic.ini upgrade head
```

В окружении процесса бота должны быть правильный адрес эмулятора и стабильный
идентификатор его истории. Например, в fish:

```fish
set -gx MAX_MODE mock
set -gx MAX_API_BASE_URL http://127.0.0.1:8081
set -gx MAX_SOURCE_ID mock-local
.venv/bin/python apps/backend/run_inbox_bot.py
```

Сетевой приём и отправка асинхронные, SQLAlchemy с синхронным psycopg выполняется
через `asyncio.to_thread`, чтобы ожидание БД не блокировало цикл событий.
Таблицы `max_inbox_events` и `max_polling_cursors` создаёт Alembic, не старт бота.
Входящие сообщения нормализуются без URL/токенов вложений; сохраняются текст,
признак фото, адресат и выбранный ответ. Это синтетический локальный стенд:
история не содержит данных, достаточных для будущего скачивания фото.

Полученная порция и её следующий marker коммитятся одной транзакцией. Если
одна запись или разбор события ошибочны, marker не продвигается. Ключ inbox:
`(source_id, bot_id, update_type, message_id)`. Повтор не создаёт новую запись
или ответ. Неподдерживаемый личный адресат/сообщение бота сохраняется как
`ignored`; событие без message ID останавливает приём без продвижения marker.

Состояния доставки:

- `pending`: ответ сохранён, отправка ещё не начата; после перезапуска продолжится;
- `sending`: перед HTTP-запросом зафиксирована попытка отправки;
- `sent`: SDK подтвердил результат, отметка сохранена;
- `unknown`: запрос завершился ошибкой; результат не считается известным;
- `ignored`: событие не требует ответа.

`sending` после аварийного завершения и `unknown` не отправляются повторно.
При запуске выводится число таких записей. Разбор пока ручной: сверьте
`/__test__/outgoing` эмулятора с inbox; команды повторной отправки нет.
Отдельная RabbitMQ/outbox-доставка относится к S1-17 и ещё не реализована.

Не меняйте MAX_SOURCE_ID при обычном перезапуске бота. После перезапуска
эмулятора его история очищается и ID переиспользуются: остановите бота и
задайте новый MAX_SOURCE_ID, например `mock-local-2`, перед запуском.
Старые записи сохранятся под прежним источником. Один poller на источник.

Контейнер БД останавливается через `docker stop vision-shield-local-pg`,
возобновляется через `docker start vision-shield-local-pg`. Том сохраняет БД.
Повторный `docker run` и генерация другого пароля для существующего тома
не меняют пароль в уже созданной БД. Сохраните первоначальное подключение
в исключённом из Git локальном окружении.

Проверка интеграции БД:

```fish
set -gx BACKEND_TEST_DATABASE_URL $BACKEND_DATABASE_URL
.venv/bin/pytest
```

Тесты создают и удаляют отдельные случайные схемы; пользователь БД должен
иметь право CREATE SCHEMA. Не используйте production-БД. Без тестового URL
PostgreSQL-тесты явно пропускаются, остальные выполняются. В CI PostgreSQL
предоставляется отдельным временным сервисом и тесты не пропускаются.

Порядок следующих изменений:

1. Проверить рабочие допущения S1-07 ниже и контракт S1-12 в PR #11.
2. Реализовать outbox/RabbitMQ-доставку по S1-17.
3. Реализовать защищённый API панели по S1-18.

## S1-06: включение согласий и приёма фото

Миграция `0002_submissions` добавляет users, campaigns, campaign_rules,
consent_prompts, consents, submissions и audit_events. Примените `upgrade head`
также к БД, где уже есть `0001`: имеющийся inbox/marker сохраняется.
Старые события не переобрабатываются в заявки. Для чистого первого демо
остановите бота, перезапустите эмулятор и выберите новый MAX_SOURCE_ID.

Создайте кампанию явно (BACKEND_DATABASE_URL должен быть экспортирован):

```bash
.venv/bin/python apps/backend/manage.py --slug local-demo --rules-version demo-v1 --rules-file apps/backend/demo-rules.txt
```

Команда выведет `BACKEND_CAMPAIGN_ID=...`. В fish установите переменную
`set -gx BACKEND_CAMPAIGN_ID "UUID_из_вывода"`, заменив содержимое кавычек
на полученный UUID. Затем запустите обычный долговечный процесс:

```bash
.venv/bin/python apps/backend/run_inbox_bot.py
```

При запуске должно быть `Приём заявок: включён`. Без UUID кампании приём
выключен; несуществующая кампания останавливает запуск, а не создаётся молча.
Файл demo-rules.txt — только синтетические демонстрационные условия,
не утверждённые правила реального сервиса.

Проверка через служебный API эмулятора (токен в MAX_EMULATOR_TOKEN):

```bash
curl -sS http://127.0.0.1:8081/__test__/messages \
  -H "Authorization: $MAX_EMULATOR_TOKEN" -H 'Content-Type: application/json' \
  -d '{"user_id":2001,"photo":true}'
```

Дождитесь ответа в `/__test__/outgoing`: он содержит UUID заявки,
`awaiting_consent`, текст правил и команду согласия. Затем:

```bash
curl -sS http://127.0.0.1:8081/__test__/messages \
  -H "Authorization: $MAX_EMULATOR_TOKEN" -H 'Content-Type: application/json' \
  -d '{"user_id":2001,"text":"/agree demo-v1"}'
```

Ожидающая заявка становится `validating`, версия увеличивается с 1 до 2,
в аудите две записи. Повторно отправленное новое фото создаёт отдельную
заявку сразу в `validating`, версия 1. Повтор доставки того же `mid` не
создаёт ещё одну заявку, согласие, запись аудита или ответ.

Для локальной Docker-БД состояние можно посмотреть напрямую:

```bash
docker exec vision-shield-local-pg psql -U postgres -d vision_shield -c 'SELECT id, status, version FROM submissions ORDER BY created_at;'
```

Рабочие допущения до завершения ревью S1-07:

- Согласие действует для пользователя, кампании и версии правил. Заявка
  ссылается на конкретное согласие. При изменении правил новые фото снова
  требуют согласия; прежние заявки сохраняют прежнюю ссылку.
- `/start` предъявляет правила, `/help` объясняет команды. `/agree ВЕРСИЯ`
  должен соответствовать текущей версии. Сокращённый `/agree` разрешён только
  после предъявления текущих правил.
- Доказательство предъявления — consent_prompts и подтверждённое состояние
  `sent` ответа с правилами. `pending`, `sending`, `unknown` не позволяют
  принять новое согласие. `/start` и `/agree` в одной ещё не отвеченной порции
  не дают согласие автоматически.
- Фото без согласия создаёт awaiting_consent и предъявляет правила. Согласие
  продвигает все ожидающие заявки этого пользователя в текущей кампании.
  Фото с подписью `/agree` считается фото, а не командой согласия.
- Имя автора не сохраняется. Случайный author_ref не раскрывает MAX-ID.
  Для синтетических источников пользователи изолированы также по source_id.
- Inbox, пользователь, согласие/заявка, аудит, ответ и marker фиксируются
  одной транзакцией. Бизнес-обработчик не делает HTTP-запросов и не коммитит
  отдельно. Пока ответ хранится в inbox; полноценная доставка S1-17 впереди.

Повтор той же команды создания кампании не меняет ID. Новая версия правил
добавляется той же командой с другим --rules-version и становится текущей.
Текст уже существующей версии менять запрещено. Работайте с кампаниями
только через административную команду, не редактированием таблиц вручную.
