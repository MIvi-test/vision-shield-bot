# Работа с репозиторием

1. Создайте ветку под задачу, например `s1-05-max-emulator`.
2. Внесите изменения, выполните доступные проверки и обновите документацию.
3. Откройте PR в целевую ветку (`develop` для текущих задач), заполните шаблон и вручную выберите ревьюера.
4. Получите минимум одно одобрение другого участника команды перед merge.

CODEOWNERS пока не используем; решение отложено до обсуждения команды.
Dev1 выполнил S1-02: реализованы проверки Python, сборка будущего фронтенда
и поиск секретов. Проверка обязательности CI выделена в S1-19.
Порядок запуска и ограничения описаны ниже.

## Проверки CI

Workflow `.github/workflows/ci.yml` запускается на каждый push и PR,
а также вручную. Имена проверок: `Python checks` и `Frontend build`.
Gitleaks работает отдельным workflow с именем проверки `Gitleaks`.
Workflow `.github/workflows/security.yml` добавляет `Dependency audit`,
`CodeQL (python)` и `CodeQL (actions)` на каждый PR, push в `main`/`develop`,
еженедельно по понедельникам в 05:17 UTC и при ручном запуске.

Добавлены проверки Ruff, типов через ty, запуск pytest и сборка фронтенда.
Тесты эмулятора уже выполняются. До появления фронтенда его сборка
пропускается автоматически. Для фронтенда настроена сборка;
тестирование UI пока не добавлено.

Python: версия 3.14, зависимости разработки задаются в корневом
`pyproject.toml` и фиксируются в `uv.lock`. Локальная установка и проверки:

```bash
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
```

Ruff проверяет стиль и форматирование, ty — совместимость типов во всём
Python-коде, включая тесты. Пути поиска модулей заданы в
`[tool.ty.environment]` в `pyproject.toml`; при добавлении приложений
с отдельными корнями импортов дополняйте `root`.
Установка ty соответствует [официальной инструкции](https://docs.astral.sh/ty/installation/).

CI запускает Ruff и ty всегда, pytest — после появления файлов `test_*.py`
или `*_test.py`. Пока тестов нет, этап pytest явно пропускается,
и причина записывается в summary. Локальный pytest без тестов возвращает код 5;
это не подтверждение прохождения тестов. Ошибки обнаружения и выполнения
существующих тестов приводят к ошибке CI.

После появления `apps/moderator-ui/package.json` CI выполняет `npm ci`
и `npm run build` в этом каталоге на Node.js 24. Dev4 должен добавить
`package-lock.json` и script `build` вместе с приложением. Отсутствие lock-файла
или команды сборки при наличии manifest приводит к ошибке CI.
До появления manifest сборка явно пропускается с записью в summary.

При добавлении библиотек Python обновляйте `pyproject.toml` и `uv.lock`
в одном PR. CI использует `uv sync --locked`: рассинхронизация этих файлов
приводит к ошибке. При подключении сервисов нужно добавить их зависимости
и тесты; текущий CI не поднимает PostgreSQL и другие сервисы.

Схема установки uv соответствует
[официальной инструкции](https://docs.astral.sh/uv/guides/integration/github/).

## Проверка зависимостей и CodeQL

CI использует uv 0.13.6. Аудит проверяет версии из `uv.lock`, включая
транзитивные зависимости и все dependency groups/extras по умолчанию:

```bash
uv lock --check
uv audit --locked
```

`--locked` запрещает обновлять lock-файл при проверке. Для аудита не требуется
устанавливать зависимости проекта или экспортировать их в `requirements.txt`.
Несогласованный lock-файл, найденная уязвимость или ошибка сервиса проверки
завершают job с ошибкой; автоматические исправления и исключения не включены.
Проверяется весь набор, а не только новые зависимости в diff PR.

Выбран встроенный [uv audit](https://docs.astral.sh/uv/reference/cli/#uv-audit):
он использует OSV и понимает lock-файл проекта. Команда находится в preview,
поэтому версия uv закреплена и проверяется при обновлении; отдельный
`pip-audit` в зависимости проекта не добавляется. Аудит известных уязвимостей
не заменяет проверку происхождения пакетов и анализ кода.

CodeQL анализирует Python и GitHub Actions с `security-extended`, без сборки
или установки зависимостей проекта. Отчёты загружаются в Code scanning;
для этой job выдано `security-events: write`, остальные job имеют только
`contents: read`. Используется обычный `pull_request`, без `pull_request_target`.
Все используемые Actions закреплены полными SHA с версией в комментарии.
При появлении frontend-кода к матрице CodeQL нужно добавить JavaScript/TypeScript.

Для CodeQL требуется доступный Code scanning (в публичном репозитории доступен)
и advanced setup. Если в настройках включён default setup, его нужно заменить
advanced setup для этого workflow. Успешная job CodeQL означает завершение
анализа, но сама по себе не запрещает merge при находках: блокировку по
серьёзности задаёт правило `Require code scanning results`, см. раздел ниже.

## Проверка секретов

Workflow `.github/workflows/secrets.yml` запускается на каждый push во все ветки
и теги, на PR и вручную; фильтров по путям нет. Запуски Gitleaks не отменяются
более новым push. Ручной запуск доступен
через Actions → Secret scan → Run workflow после появления workflow в default branch
(сейчас `develop`).
Gitleaks 8.30.1 проверяет всю доступную Git-историю, включая секреты,
удалённые последующими коммитами. Значения находок скрываются в логах;
при находке проверка завершается с ошибкой. Дополнительные токены и лицензии
для запуска не нужны.

Локально с установленным Gitleaks 8.30.1:

```bash
gitleaks git . --log-opts="--all" --redact --no-banner --exit-code=1
```

Команда проверяет коммиты; незакоммиченные изменения в неё не входят.
При реальной утечке сначала отзовите или замените секрет: удаление из текущего
файла не убирает его из истории. Ложные срабатывания разбирайте с ревьюером,
без исключения целых каталогов из проверки.

## Защита main и develop

Файлы репозитория не включают защиту ветки автоматически. Администратор
настраивает её в GitHub: Settings → Branches → Add branch protection rule.
Правила применяются к `main` и `develop`, поскольку рабочие PR идут в `develop`.

- Требовать PR и минимум одно одобрение.
- Сбрасывать одобрения при новых изменениях в PR.
- Требовать разрешения обсуждений перед merge.
- Разрешить администраторам обход защиты; для остальных участников правила обязательны.
- Запретить force push и удаление ветки.

Обязательное ревью CODEOWNERS не включать. Обязательные status checks
добавить и проверить в S1-19, используя реальные имена проверок.

Проверка настройки для участника без прав администратора: прямой push в защищённую ветку
и merge PR без одобрения должны блокироваться GitHub.

Защита `main` проверена через GitHub API 22 октября 2026: требуется одно одобрение,
новые изменения сбрасывают одобрения, обсуждения должны быть разрешены;
force push и удаление запрещены. Администраторы могут обходить защиту.
CODEOWNERS и обязательные status checks не включены.
После первого запуска новых workflow добавьте `Gitleaks`, `Python checks`,
`Frontend build`, `Dependency audit`, `CodeQL (python)` и `CodeQL (actions)`
в обязательные status checks защиты обеих веток, сверив реальные имена в Actions.
До настройки required checks ошибка CI сама по себе не блокирует merge.
Затем проверьте на тестовом PR, что ошибка Ruff, ty или pytest блокирует merge.

Для блокировки находок CodeQL добавьте в ruleset обеих веток
`Require code scanning results` с инструментом CodeQL и порогом security alerts
`High or higher` (обычные alerts — `Errors`). Настройка и проверка описаны в
[документации GitHub](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/manage-your-configuration/set-merge-protection).
Проверьте отдельно отклонение PR с уязвимой зависимостью и CodeQL alert нужной
серьёзности. Файлы workflow не включают эти правила GitHub автоматически;
их фактическая работа подтверждается в S1-19 после запуска в GitHub.
S1-02 остаётся выполненной задачей Dev1. Проверка блокировки merge — S1-19;
реальная сборка появляющейся панели — S1-11 и совместная приёмка S1-16.
