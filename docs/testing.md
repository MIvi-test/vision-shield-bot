# План тестирования

Часть архитектурной документации; обзор и карта документов — в [ARCHITECTURE.md](ARCHITECTURE.md).

Тесты пишет владелец кода; этот раздел задаёт виды тестов, общий стенд и правила допуска. Владелец раздела — Dev4; отказные и нагрузочные прогоны ведёт Dev1.

| Вид | Что проверяет | Инструмент | Когда запускается | Владелец |
| --- | --- | --- | --- | --- |
| Unit | Доменные правила, переходы состояний, политика модерации, компоненты UI | pytest; для UI — Vitest | Каждый PR | Владелец кода |
| Контрактные | Схемы событий из `packages/contracts`, OpenAPI панели, совпадение эмулятора с записанными ответами MAX | pytest, валидация схем | Каждый PR | События и эмулятор — Dev2 и Dev3; OpenAPI — Dev4 |
| Интеграционные | Backend и workers с настоящими PostgreSQL, RabbitMQ и MinIO | pytest, Compose в CI | Каждый PR после появления конвейера | Dev2 |
| E2E | Эмулятор → публикация → уведомление; ручная модерация через панель | pytest против стенда; Playwright для панели, когда понадобится | Merge в `main` | Сценарий — Dev2, панель — Dev4 |
| Негативные и security | Повреждённые, слишком большие и полиглот-файлы, бомбы декомпрессии; обход ролей, доступ к чужой заявке, истёкший presigned URL, CSRF; отсутствие секретов и ПДн в логах | pytest, набор вредоносных файлов в изолированном стенде | Merge в `main` и перед демо | Dev4; файлы — вместе с Dev2 |
| Отказные | Падение worker до ACK; недоступные брокер, PostgreSQL или MinIO; таймаут MAX после фактической отправки | Сценарии fault injection на стенде | Перед демо и после изменений надёжности | Dev1 |
| Нагрузочные | p50/p95 задержек, CPU/RAM CV, поведение очередей под нагрузкой | k6 или скрипт генерации заявок | Перед демо | Dev1; CV — вместе с Dev3 |
| Оценка модели | precision/recall, доля ручной проверки, задержка, RAM | Скрипт оценки на фиксированном наборе | При смене модели, весов или порогов | Dev3; наборы — Dev4 |

**Тестовые данные:** фиксированный набор изображений с воспроизводимой загрузкой — подходящие, неподходящие, пограничные, запрещённые, пограничные форматы, дубли и сгенерированные вредоносные файлы. Для каждого записаны источник и лицензия ([security.md](security.md) §3). Вредоносные файлы открываются только в изолированном стенде.

**Правила допуска:**

- CI с первого спринта: Ruff и форматирование, типы, unit, контрактные тесты, frontend checks/build, поиск секретов и уязвимых зависимостей, сборка образов. После появления конвейера добавляются интеграционные тесты. PR не мержится без зелёного CI.
- Изменение контракта сопровождается обновлением контрактных тестов у обеих сторон.
- Перед демо — полный прогон e2e, security, отказных и нагрузочных тестов. Результаты с датой, версией и конфигурацией стенда сохраняются в `docs/results/`.

**Обязательные проверки** — каждая оформлена автоматическим тестом или записанным сценарием:

- вход: дубликат входного события; повтор того же файла в кампании; превышение входного и исходящего rate limit; истёкшая ссылка на вложение;
- надёжность: падение worker до ACK; повтор результата после confirm; недоступный брокер при сохранённом outbox; очистка orphan без удаления активного объекта;
- решения и публикация: конкурентные решения модераторов (`409`); отмена во время публикации; таймаут MAX после фактической отправки; повторный запуск розыгрыша;
- безопасность: повреждённое или слишком большое изображение; запрещённый доступ к фото;
- эмулятор: расхождение с записанными ответами MAX.

**Откуда берутся метрики постановки:**

| Метрика из assignment.md | Где измеряется |
| --- | --- |
| precision/recall модерации | Оценка модели на фиксированном наборе |
| p50/p95 «приём → решение» и «решение → публикация» | Нагрузочный прогон по временным меткам заявок |
| Доля заявок, восстановленных после временного сбоя | Отказные сценарии |
| Число предотвращённых дублей | Интеграционные и e2e-тесты с дублями; метрика стенда |
| Число отклонённых невалидных файлов | Security-прогон на наборе невалидных файлов; метрика стенда |
| Результаты негативных и security-тестов | Security-прогон, отчёт в `docs/results/` |
