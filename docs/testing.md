# План тестирования

Часть архитектурной документации; обзор и карта документов — в [ARCHITECTURE.md](ARCHITECTURE.md).

Тесты пишет владелец кода. Dev4 ведёт требования проверок, Dev1 подключает команды к CI и организует отказные/нагрузочные прогоны. Для совместного сценария каждый владелец проверяет свою часть; вся интеграция не возлагается на Dev2.

## Виды проверок

| Вид | Что проверяет | Инструмент | Когда | Владелец |
| --- | --- | --- | --- | --- |
| Unit | Доменные правила, обработка файлов, политика, компоненты UI | pytest; Vitest для UI | PR соответствующего компонента | Владелец кода |
| Контрактные | Схемы событий, OpenAPI, формы ответов эмулятора по фикстурам MAX | pytest, валидация схем | PR с контрактом или взаимодействующей реализацией | События — Dev2/Dev3, OpenAPI — Dev4/Dev2, эмулятор — Dev1 с ревью Dev2 |
| Интеграционные | Backend и workers с PostgreSQL, RabbitMQ и MinIO по мере их появления | pytest, Compose в CI | PR после появления соответствующего пути | Dev2 — Backend/fetcher/publisher; Dev3 — media/CV; Dev1 — запуск |
| E2E | Первый приём, ручной путь, затем автоматический путь до публикации | pytest против стенда; браузерные проверки при необходимости | PR с изменением сценария и перед демо | Dev2 — жизненный цикл, Dev3 — обработка, Dev4 — UI, Dev1 — стенд/CI |
| Негативные и security | Файлы, источники скачивания, роли, CSRF, превью, безопасные логи | pytest, изолированный стенд | Вместе с соответствующей функцией | Dev4; исправления Dev2/Dev3, изоляция Dev1 |
| Отказные | Падение до ACK, недоступные зависимости, неоднозначная внешняя отправка | Управляемые сбои эмулятора и стенда | Базовые — с файловым путём; расширенные — после MVP | Dev1 с владельцем компонента |
| Нагрузочные | p50/p95, CPU/RAM, очереди и перегрузка | Скрипт генерации заявок или k6 при необходимости | После появления полного пути; итоговый профиль перед выпуском | Dev1; media/CV — Dev3 |
| Качество модели | Ошибочные решения, precision/recall по классам, доля ручной проверки, время/RAM | Воспроизводимый скрипт оценки | До автопубликации и при смене модели/политики | Dev3; данные — Dev4 |

## Приёмка по этапам

| Этап | Обязательные проверки |
| --- | --- |
| Спринт 1: запускаемая основа | Согласие с версией правил; одна заявка при повторе события; сохранение marker после коммита; доставка сохранённого ответа; вход и права панели; реальные тесты Backend/эмулятора и сборка UI; запуск по README |
| Спринт 2: ручной путь | Реальные скачивание и очистка; технические отказы, EXIF и дубли; запрет доступа к оригиналу; ручные решения и `409`; публикация и уведомление; базовые лимиты; повтор задачи/результата; падение worker до ACK; `publication_unknown` без слепого повтора |
| Спринт 3: MVP | Три исхода настоящего CV, ошибка модели и ручная ветка; проверка версий и поздних результатов; контрольная оценка качества; e2e MVP, изоляция и применимые security/DAST-проверки |
| После MVP | Расширенные отказы БД/брокера/MinIO; контролируемый DLQ; сверка и отмена во время публикации; отзыв согласия, сроки хранения и очистка orphan; восстановление резервной копии; рейтинг/розыгрыш и повтор callback; реальный MAX при доступности; обновление и нагрузочный профиль |

Компонент принимается на собственных тестах без ожидания всей системы. Сквозная приёмка оформляется отдельной задачей (S1-16, S2-10, S3-06). Реализованный Dev1 эмулятор S1-05 имеет собственные SDK/контрактные тесты; отсутствие Backend не отменяет этот результат. CI и инструменты S1-02 также выполнены; обязательность checks отдельно проверяется в S1-19.

## Данные и правила допуска

- Dev3 задаёт критерии разметки и критерии качества в спринте 1. Dev4 готовит первые примеры тогда же, полный набор для настройки и контроля — в спринте 2. Контрольные данные не используются для выбора порогов. Состав, версии, источники и лицензии воспроизводимы.
- Файловые тесты включают корректные, повреждённые, слишком большие, пограничные и синтетические вредоносные примеры. Проверяются форматы по содержимому, несовпадение MIME и обнаруженный в S1-04 WEBP согласно принятой политике. Недоверенные файлы открываются только в изолированном стенде.
- Детерминированные CV-заглушки проверяют ошибки и маршрутизацию; они не заменяют отчёт качества или демо настоящей модели. Промежуточный рабочий сценарий использует явный ручной режим, а не имитацию очистки.
- Выполненный CI запускает Ruff, форматирование, ty, pytest и Gitleaks. Сборка UI уже предусмотрена и реально выполняется после появления manifest/lockfile/build. Проверки образов, зависимостей и SAST добавляются с файловым стендом в спринте 2; DAST — к MVP. Пропущенный этап явно виден и не считается проверкой отсутствующего приложения.
- Контракт меняется вместе с примерами и проверками обеих сторон. Сборка нового приложения подключается в том же этапе, где приложение появляется.
- Перед демо проверяется готовый к этому этапу сценарий и применимые отказы/защиты. Полный нагрузочный прогон не требуется для первого списка заявок. Результаты содержат дату, версию, данные и конфигурацию.
- Критерии MVP — в [mvp.md](mvp.md#готовность-mvp). Блокирующие проблемы исправляются до приёмки; одного заведения задачи недостаточно.

## Метрики постановки

| Метрика из assignment.md | Подтверждение |
| --- | --- |
| precision/recall модерации | Контрольная оценка до автопубликации |
| p50/p95 «приём → решение» и «решение → публикация» | Прогон по временным меткам на указанной нагрузке |
| Доля заявок, восстановленных после временного сбоя | Отказные сценарии с числом поданных и восстановленных заявок |
| Число предотвращённых дублей | Интеграционные/e2e-проверки и счётчик стенда |
| Число отклонённых невалидных файлов | Файловый набор, результаты media и счётчик стенда |
| Результаты негативных и security-тестов | Отчёт с проверкой, результатом и ограничением |
