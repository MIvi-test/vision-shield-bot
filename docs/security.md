# Безопасность и персональные данные

Обработка недоверенных файлов, меры защиты и правила работы с персональными данными. Часть архитектурной документации; обзор и карта документов — в [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Файловый конвейер

Оригиналы в `quarantine/` пишет только fetcher и читает только media. CV, UI и publisher получают только `sanitized/`. Отдельная копия `published/` не обязательна.

Media проверяет фактический формат, размер файла, число пикселей/кадров, время и память декодирования; затем применяет ориентацию, перекодирует в разрешённый формат и удаляет EXIF и прочие ненужные метаданные. Начальный набор форматов — JPEG/PNG; лимиты фиксируем в конфигурации после измерений. Очистка уменьшает риск, но не заменяет ограничения декодера.

Fetcher принимает только источники вложений, разрешённые MAX-адаптером: проверяет хосты и редиректы, запрещает произвольные URL и доступ к внутренним адресам, ограничивает размер и время скачивания. Содержимое файла fetcher не декодирует. CV использует внутренний ключ объекта, а не URL от пользователя.

S3 и PostgreSQL не образуют общую транзакцию. Ключи объектов привязываем к операции; Backend регистрирует объект после записи fetcher и результат после сообщения media. Очистка удаляет осиротевшие объекты лишь после защитного интервала, превышающего окно обработки и повторов, и проверки ссылок/активных операций. Срок хранения оригиналов, очищенных фото и аудита фиксируем до демо с реальными данными.

Предпросмотр выдаёт Backend после проверки прав через короткий presigned URL. Ссылки и токены не попадают в логи; адрес MinIO для браузера и внутренний адрес для workers настраиваем отдельно.

## 2. Меры защиты

- Dev4 (AppSec) владеет моделью угроз (`docs/threat-model.md`) и security-checklist (`docs/security-checklist.md`) и вместе с Dev2 проверяет обработку недоверенных файлов. Dev1 (DevSecOps) отвечает за инфраструктурные меры: секреты, сети, hardening контейнеров, проверки в CI.
- CV и media запускаются non-root, без Docker socket, с `no-new-privileges`, сброшенными capabilities, read-only rootfs, ограниченным tmpfs и CPU/RAM/PID.
- Две сети Compose: `app` для Backend и инфраструктуры; `processing` с `internal: true` для media, CV, RabbitMQ и MinIO. Media и CV подключены только к `processing`, PostgreSQL там отсутствует. RabbitMQ и MinIO доступны в обеих сетях; не настраиваем через них проксирование наружу. Модель загружается заранее. Это сетевой барьер, дополненный правами брокера и хранилища. [Compose networks](https://docs.docker.com/reference/compose-file/networks/).
- Доступ к MAX имеют только Backend-процессы: выборочный egress средствами Compose без отдельного прокси не выразить, поэтому скачивание вложений вынесено в fetcher, а media остаётся без интернета. Разбор файла в media выполняется отдельным ограниченным процессом.
- RabbitMQ: разные credentials и разрешения очередей. MinIO: fetcher пишет в `quarantine/`, media читает `quarantine/` и пишет в `sanitized/`, CV и publisher читают только `sanitized/`. Media и CV не получают MAX-токен.
- Rate limiting в Redis: на входе — по пользователю для фото и callback; на выходе — общий счётчик на чат или канал для publisher и notifier, чтобы вместе не превысить лимит MAX ([contracts.md](contracts.md) §4).
- Backend проверяет авторизацию и роли на каждой операции: moderator — решения, organizer — розыгрыш, admin — настройки. UI лишь отображает доступные действия. Для cookie-сессий нужны HttpOnly/SameSite и защита CSRF.
- Секреты храним в исключённых из Git `.env` или файлах стенда с ограниченными правами; `.env.example` содержит только шаблоны. Логи исключают токены, подписанные URL и содержимое фото. Размер входных данных ограничиваем на каждом шаге.

## 3. Персональные данные и privacy

Принцип — минимизация: храним только то, что нужно для публикации, модерации, уведомлений и розыгрыша. Владелец раздела — Dev4. Сроки хранения и правило отзыва согласия ниже — предложение, команда утверждает их до демо с реальными данными.

| Данные | Зачем | Кто видит | Срок хранения (предложение) |
| --- | --- | --- | --- |
| MAX `user_id`, `chat_id` | Связать заявку с автором, отправить уведомление | Backend; в панели — внутренний ID автора | Пока у пользователя есть заявки |
| Имя пользователя из MAX | Объявление победителей | Организатор | Не храним, пока не нужен розыгрыш; затем до его закрытия |
| Оригинал фото | Проверка и очистка | Только media | Удаляется после обработки и окна повторов |
| Очищенное фото | Модерация, публикация, предпросмотр | Модератор; канал после публикации | Пока заявка активна или опубликована; после отказа или удаления поста — короткий срок, затем удаление |
| Согласие: пользователь, версия правил, время | Подтвердить право на публикацию | Backend, аудит | Пока хранятся заявки пользователя |
| Голоса | Рейтинг и защита от накруток | Backend; организатор — только итоги | До закрытия розыгрыша, затем остаётся снимок |
| Снимок розыгрыша и победители | Воспроизводимость результата | Организатор | До конца проекта |
| Аудит | История решений | Модератор, разработчики | До конца проекта, без содержимого фото |
| Логи | Диагностика | Разработчики | Короткая ротация, только внутренние ID |

- EXIF и прочие метаданные, включая геолокацию, удаляются при очистке (§1). Оригинал не публикуется и не показывается в панели.
- В логах, метриках, сообщениях очередей и DLQ — только внутренние ID: без имён, содержимого фото, токенов и presigned URL ([contracts.md](contracts.md) §1 и §2 этого документа).
- Текст правил, на которые соглашается пользователь, описывает публикацию в канале, автоматическую и ручную проверку, участие в рейтинге и розыгрыше, сроки хранения. Каждая версия текста хранится; согласие ссылается на версию.
- Отзыв согласия: новые заявки не принимаются; опубликованные посты автора удаляются по жизненному циклу публикации ([data-model.md](data-model.md) §3); заявки и голоса исключаются из рейтинга; очищенные фото удаляются; в аудите остаётся запись об отзыве без персональных данных. Запрос на удаление данных обрабатывается так же.
- Доступ к данным в панели ограничен ролями (§2). Список пользователей организатор видит только в объёме победителей розыгрыша.
- Тестовые данные — только открытые и синтетические изображения с записанным источником и лицензией. Фото реальных людей — только с их согласия; на демо — тестовые аккаунты.
