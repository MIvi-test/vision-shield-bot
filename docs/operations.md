# Запуск и диагностика

Окружения, запуск стенда, логи и метрики. Часть архитектурной документации; обзор и карта документов — в [ARCHITECTURE.md](ARCHITECTURE.md).

У каждого разработчика — свой бот или эмулятор, отдельные данные и локальные секреты. На демо — один общий тестовый бот. Целевые режимы конфигурации: `MAX_MODE=mock|polling|webhook`; сейчас Backend поддерживает только mock. Для polling нужен один активный получатель на токен и отключённая webhook-подписка.

Сейчас доступны [эмулятор MAX v0](../apps/max-emulator/README.md), Backend
с PostgreSQL-inbox и начальный Compose ниже. Каркас панели запускается
опционально; API панели и outbox-доставка ещё не реализованы.
MinIO, Redis и изолированные workers добавляются в спринте 2.
Команды приложений и тесты предоставляют их владельцы, Dev1 подключает их
к окружению и CI.

## Локальный Compose (S1-03)

Нужны Docker Engine с Compose v2+ и свободные порты 8000/8081.
Если они заняты, измените `BACKEND_PORT`/`MAX_EMULATOR_PORT` в `.env`.

Подготовка из корня репозитория:

```bash
cp .env.example .env
openssl rand -hex 24
openssl rand -hex 24
```

Впишите два разных результата в `POSTGRES_PASSWORD` и `RABBITMQ_PASSWORD`
локального `.env`. Пароль PostgreSQL используется внутри URL, поэтому
используйте предложенный hex-формат; имена БД и пользователя тоже оставьте
URL-safe. Пустые пароли останавливают Compose до создания контейнеров.
Реальный MAX-токен не нужен и в контейнеры не передаётся.
Compose читает `.env` для подстановки, но не передаёт весь файл сервисам.
Не публикуйте вывод `docker compose config`: он содержит заполненные секреты.

```bash
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps -a
```

PostgreSQL проходит TCP-healthcheck (временный сервер инициализации,
слушающий только Unix-сокет, не считается готовым), затем `migrate` выполняет `upgrade head`
и завершается с кодом 0. После миграций запускаются HTTP-сервер и inbox-бот;
бот также ждёт готовности эмулятора. `backend` проверяет только HTTP liveness,
`--wait` не подтверждает обработку события ботом: для этого выполните демо ниже.
Порядок зависимостей использует условия
[Compose](https://docs.docker.com/compose/how-tos/startup-order/).
Образы приложений собираются с `uv 0.13.6`, `uv sync --locked --no-dev`
по [рекомендациям uv](https://docs.astral.sh/uv/guides/integration/docker/).

| Сервис | Назначение и доступ |
| --- | --- |
| `postgres` | PostgreSQL 18, постоянный том; порт на хост не публикуется |
| `rabbitmq` | Брокер с постоянным томом и стабильным hostname; порты не публикуются |
| `migrate` | Одноразовое применение миграций; ожидаемый статус `Exited (0)` |
| `backend` | HTTP liveness на `http://127.0.0.1:8000/health/live`, Swagger `/docs` |
| `max-emulator` | SDK API и Swagger на `http://127.0.0.1:8081/docs` |
| `bot` | Один polling-процесс с inbox; без кампании только проверка связи |
| `moderator-ui` | Профиль `frontend`: каркас панели на `http://127.0.0.1:8080`, Caddy и proxy к Backend |

Для запуска панели вместе с HTTP Backend и БД:

```bash
docker compose up --build -d --wait moderator-ui backend
```

Только панель: `docker compose up --build -d --wait moderator-ui`.
Весь стенд с панелью: `docker compose --profile frontend up --build -d --wait`.
При работающем стенде используйте команду с конкретными сервисами, чтобы
не пересоздавать эмулятор. По умолчанию профиль выключен. `PANEL_PORT` меняет
локальный порт, `PANEL_BACKEND` — внутренний upstream Caddy (`backend:8000`).
Проверка здоровья панели не зависит от Backend; без него proxy возвращает 502.
API панели пока отсутствует. [Подробности запуска](../apps/moderator-ui/README.md#запуск-через-compose).

RabbitMQ пока не используется ботом: outbox/dispatcher/notifier относятся
к S1-17. Постоянный том брокера не заменяет durable-очереди и проверку их
восстановления после реализации доставки. Приёмка панели остаётся в S1-11.
Полная приёмка S1-03 и совместный сценарий S1-16 остаются открыты.

### Автоматический smoke-тест

Из корня репозитория, с Python 3.14 и работающим Docker Compose 2.24.4+:

```bash
python3 infra/scripts/smoke_compose.py
```

Дополнительные Python-зависимости не нужны. Команда собирает оба образа,
создаёт случайный Compose project, отдельные image tags и пустые тома,
генерирует временные credentials и публикует HTTP на случайных loopback-портах.
Рабочий `.env` и экспортированные настройки проекта не используются.
Для замены портов применяется
[`!override` Compose](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/),
доступный начиная с 2.24.4.

Проверяются миграции до текущего head, HTTP liveness, фото до согласия,
согласие после доставки правил, версии/аудит/ответы в БД, перезапуск бота,
повторное чтение тех же событий без дублей, сохранение БД при пересоздании
контейнеров PostgreSQL/RabbitMQ и продолжение обработки после этого.
Для проверки повтора marker сбрасывается только в одноразовой тестовой БД;
эмулятор сохраняет свою историю до конца сценария.

При успехе и обычной ошибке команда собирает диагностику и удаляет только
свой случайный проект: контейнеры, сеть и тестовые тома. Рабочие тома
`vision-shield` не затрагиваются. Собранные образы/кеш Docker остаются.
При принудительном SIGKILL очистка не гарантируется; имя проекта напечатано
при запуске и записано в `result.json`.

В `tmp/compose-smoke/<project>/` (исключён из Git) остаются `result.json`,
`commands.log`, `services.json`, `services.log`. Лог команд содержит также
вывод сборки. Credentials скрываются перед записью; временный env-файл
находится отдельно с правами 0600 и не включается в артефакты.
Путь можно изменить через `--artifacts-dir`.

CI запускает ту же команду в job `Compose smoke` на push/PR и вручную;
артефакты загружаются даже при ошибке и хранятся 7 дней. Новый job сам
по себе не становится обязательным check в ruleset GitHub.
UI, файловый конвейер и настоящая доставка через RabbitMQ этим тестом
не проверяются; совместная приёмка S1-16 остаётся отдельной задачей.

### Ресурсные ограничения

У каждого сервиса заданы CPU/RAM/PID и ротация логов. Бюджеты и их
обоснование — в [плане ресурсов, §6](results/capacity-planning.md#6-лимиты-начального-compose).
PostgreSQL ограничен 1536 МиБ, RabbitMQ — 512 МиБ; HTTP Backend и бот —
по 384 МиБ, миграции — 256 МиБ (вместе 1 ГиБ), эмулятор — 256 МиБ отдельно.
Опциональная панель получает 96 МиБ, 0,5 CPU и лимит 64 PID.
Swap сверх этих лимитов отключён. Для полного стенда ориентир остаётся
4 vCPU / 16 ГиБ, а текущие CPU/PID-квоты требуют проверки под нагрузкой.

RabbitMQ получает memory alarm при 256 МиБ и ограниченное число Erlang
потоков. Логи контейнера ротируются по 10 МиБ, максимум три файла;
это не ограничивает рост данных в томах.

После изменения лимитов пересоздайте нужные контейнеры: простой `restart`
не применяет конфигурацию. Пересоздание эмулятора требует остановки бота
и нового `MAX_SOURCE_ID` по разделу ниже. Текущее потребление:

```bash
docker compose stats --no-stream
```

### Включить приём заявок и пройти демо

Создайте синтетическую кампанию штатной административной командой:

```bash
docker compose run --rm --no-deps bot python apps/backend/manage.py --slug local-demo --rules-version demo-v1 --rules-file apps/backend/demo-rules.txt
```

Запишите напечатанный UUID в `BACKEND_CAMPAIGN_ID` в `.env`, затем пересоздайте
только бота, сохраняя историю эмулятора:

```bash
docker compose up -d --no-deps bot
docker compose logs --tail=30 bot
```

В логах должно быть `Приём заявок: включён`. Для запросов ниже экспортируйте
в терминале `MAX_EMULATOR_TOKEN` с тем же синтетическим значением, что в `.env`.
Адреса соответствуют портам по умолчанию.

```bash
curl -fsS http://127.0.0.1:8000/health/live
curl -fsS http://127.0.0.1:8081/__test__/messages \
  -H "Authorization: $MAX_EMULATOR_TOKEN" -H 'Content-Type: application/json' \
  -d '{"user_id":2001,"photo":true}'
curl -fsS http://127.0.0.1:8081/__test__/outgoing \
  -H "Authorization: $MAX_EMULATOR_TOKEN"
```

Дождитесь ответа с UUID заявки и правилами. После подтверждённого ответа:

```bash
curl -fsS http://127.0.0.1:8081/__test__/messages \
  -H "Authorization: $MAX_EMULATOR_TOKEN" -H 'Content-Type: application/json' \
  -d '{"user_id":2001,"text":"/agree demo-v1"}'
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id, status, version FROM submissions ORDER BY created_at;"'
```

После обработки согласия заявка имеет `validating`, версия 2. Фотография
пока не скачивается и не обрабатывается. Подробнее — [Backend](../apps/backend/README.md).

### Остановка, перезапуск и данные

```bash
docker compose stop bot
docker compose start bot
docker compose logs --tail=50 bot migrate
```

Обычный перезапуск бота сохраняет `MAX_SOURCE_ID`, marker, согласия и заявки.
Не масштабируйте `bot`: на источник нужен один получатель.
При остановке боту передаётся SIGINT и даётся до 30 секунд на завершение;
это не гарантирует известный исход уже начатого внешнего запроса.

`docker compose down` удаляет контейнеры/сеть, но сохраняет тома БД и брокера.
`docker compose stop` сохраняет контейнеры, однако при следующем запуске
эмулятор всё равно начинает новую историю: его данные живут в памяти процесса.
Перед любым перезапуском/пересозданием эмулятора остановите бота, измените
`MAX_SOURCE_ID` в `.env` на новое уникальное значение и запустите стенд снова.
Не используйте старое имя источника после сброса истории. Старые заявки
останутся в БД; согласие для нового синтетического источника запрашивается заново.
Перед сменой источника проверьте незавершённые ответы:

```bash
docker compose exec -T postgres sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT source_id, state, count(*)
FROM max_inbox_events
WHERE state IN ('pending', 'sending', 'unknown')
GROUP BY source_id, state;
SQL
```

`pending` старого источника не доставляется ботом нового источника.
`sending`/`unknown` требуют отдельной сверки: смена `MAX_SOURCE_ID`
не подтверждает доставку и не разрешает автоматически повторять отправки.
Для контейнеров не задан автоматический restart, чтобы сброс истории эмулятора
не происходил незаметно.

При обновлении образа Backend остановите бота и HTTP-сервис, примените миграции
и запустите процессы, сохранив работающий эмулятор:

```bash
docker compose stop bot backend
docker compose build
docker compose run --rm migrate
docker compose up -d --no-deps backend bot
```

Смена паролей в `.env` не меняет credentials уже созданной БД/брокера.
Не удаляйте тома ради обычного перезапуска. `docker compose down --volumes`
необратимо удаляет локальные данные; используйте только для намеренного
полного сброса тестового стенда. Бэкапы и проверка восстановления — S4-05.

## Целевой демо-стенд и эксплуатация

При локальном демо без домена интерфейс доступен через localhost или SSH-туннель. Публичный доступ к панели с учётными данными требует HTTPS; отсутствие webhook не отменяет защиту панели. Демонстрационный сервер обновляем вручную фиксированной версией образов, после проверки миграций и резервной копии.

После MVP цель — проверенная ограниченная эксплуатация на одном стенде. До неё фиксируются аудитория, ожидаемая нагрузка, CPU/RAM/диск, ответственный, условия хранения данных и допустимое время восстановления. Для реальной эксплуатации MAX используется webhook по [contracts.md](contracts.md#4-интеграция-с-max); polling остаётся режимом разработки/тестового демо. Если условия не подтверждены, результат обозначается учебным или тестовым.

В спринте 4 проверяются метрики, оповещения, резервное копирование и восстановление БД вместе с объектами на пустом окружении. Фиксируются время восстановления и возможная потеря данных. Перед выпуском проверяются обновление, миграции и действия при неудаче; откат данных не предполагается автоматически безопасным.

Логи содержат `submission_id`, `operation_id`, `event_id`, компонент и причину ошибки. Основные метрики:

- метрики из постановки: p50/p95 «приём → решение» и «решение → публикация», доля заявок, восстановленных после временного сбоя, число предотвращённых дублей и отклонённых невалидных файлов, precision/recall модерации ([moderation.md](moderation.md));
- эксплуатационные: возраст outbox, глубина очередей/DLQ, ошибки workers, длительность CV, срабатывания rate limit, операции с неизвестным исходом, CPU/RAM.

Readiness CV проверяет загрузку модели. Численные цели задержки фиксируем после замеров на известных изображениях и ресурсах; результаты замеров, отказных и нагрузочных тестов сохраняем в `docs/results/`.
