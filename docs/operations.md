# Запуск и диагностика

Окружения, запуск стенда, логи и метрики. Часть архитектурной документации; обзор и карта документов — в [ARCHITECTURE.md](ARCHITECTURE.md).

У каждого разработчика — свой бот или эмулятор, отдельные данные и локальные секреты. На демо — один общий тестовый бот. Целевые режимы конфигурации: `MAX_MODE=mock|polling|webhook`; Backend ещё не реализован. Для polling нужен один активный получатель на токен и отключённая webhook-подписка.

Сейчас самостоятельно запускается [эмулятор MAX v0](../apps/max-emulator/README.md), выполненный Dev1 в S1-05; CI и инструменты проверок выполнены в S1-02. Полный стенд ещё предстоит собрать. В спринте 1 Compose объединяет Backend, PostgreSQL, RabbitMQ, эмулятор и панель; MinIO, Redis и изолированные workers добавляются в спринте 2. Команды приложений и тесты предоставляют их владельцы, Dev1 подключает их к окружению и CI.

Целевой запуск после реализации Compose:

```bash
cp .env.example .env
docker compose up --build -d
```

При локальном демо без домена интерфейс доступен через localhost или SSH-туннель. Публичный доступ к панели с учётными данными требует HTTPS; отсутствие webhook не отменяет защиту панели. Демонстрационный сервер обновляем вручную фиксированной версией образов, после проверки миграций и резервной копии.

После MVP цель — проверенная ограниченная эксплуатация на одном стенде. До неё фиксируются аудитория, ожидаемая нагрузка, CPU/RAM/диск, ответственный, условия хранения данных и допустимое время восстановления. Для реальной эксплуатации MAX используется webhook по [contracts.md](contracts.md#4-интеграция-с-max); polling остаётся режимом разработки/тестового демо. Если условия не подтверждены, результат обозначается учебным или тестовым.

В спринте 4 проверяются метрики, оповещения, резервное копирование и восстановление БД вместе с объектами на пустом окружении. Фиксируются время восстановления и возможная потеря данных. Перед выпуском проверяются обновление, миграции и действия при неудаче; откат данных не предполагается автоматически безопасным.

Логи содержат `submission_id`, `operation_id`, `event_id`, компонент и причину ошибки. Основные метрики:

- метрики из постановки: p50/p95 «приём → решение» и «решение → публикация», доля заявок, восстановленных после временного сбоя, число предотвращённых дублей и отклонённых невалидных файлов, precision/recall модерации ([moderation.md](moderation.md));
- эксплуатационные: возраст outbox, глубина очередей/DLQ, ошибки workers, длительность CV, срабатывания rate limit, операции с неизвестным исходом, CPU/RAM.

Readiness CV проверяет загрузку модели. Численные цели задержки фиксируем после замеров на известных изображениях и ресурсах; результаты замеров, отказных и нагрузочных тестов сохраняем в `docs/results/`.
