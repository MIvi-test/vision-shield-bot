# Контракты и надёжность

Как компоненты обмениваются событиями, какие гарантии доставки мы даём и как устроена интеграция с MAX. Часть архитектурной документации; обзор и карта документов — в [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. События и очереди

В репозитории храним одну версионированную схему событий. Бинарные файлы, токены и долгоживущие публичные ссылки в очередь не кладём.

```json
{
  "schema_version": 1,
  "event_id": "uuid",
  "event_type": "cv.completed",
  "correlation_id": "submission-uuid",
  "submission_id": "submission-uuid",
  "operation_id": "moderation-run-uuid",
  "causation_id": "request-event-uuid",
  "occurred_at": "2026-10-21T12:00:00Z",
  "payload": {
    "asset_id": "asset-uuid",
    "policy_version": "nature-v1",
    "model_version": "model-and-weights-version",
    "recommended_decision": "review_required",
    "scores": {"topic": 0.73},
    "reason_codes": ["LOW_TOPIC_CONFIDENCE"]
  }
}
```

`event_id` идентифицирует событие и сохраняется при повторной доставке. `operation_id` идентифицирует логический запуск обработки; новая модерация получает новый ID. Backend принимает результат только для ожидаемых операции, объекта и версии правил. Поздний ответ CV не отменяет более новое решение модератора.

| Очередь | Производитель → потребитель | Содержание |
| --- | --- | --- |
| `fetch.tasks` | Backend outbox → Backend fetcher | Идентификатор вложения от MAX-адаптера, ключ объекта в карантине |
| `media.tasks` | Backend outbox → media | Ключ оригинала в карантине и разрешённые ключи очищенных объектов |
| `cv.tasks` | Backend outbox → CV | `asset_id`, ключ очищенного объекта, снимок политики |
| `backend.results` | Media/CV → Backend consumer | Результат или классифицированная ошибка операции |
| `publication.tasks` | Backend outbox → Backend publisher | ID операции публикации или удаления |
| `notification.tasks` | Backend outbox → Backend notifier | ID сохранённого уведомления |

## 2. Outbox, inbox и ACK

Outbox и идемпотентность входят в первый вертикальный сценарий.

- **Вход MAX:** уникальность по источнику, боту и стабильному ключу события. Правило ключа задаём для каждого типа обновления; не предполагаем наличие универсального ID в MAX. Для callback используем его идентификатор; для сообщения — идентичность сообщения и тип события.
- **Polling:** один poller на токен. Следующий `marker` сохраняем вместе с надёжно записанной полученной порцией; продвигаем его после коммита. После сбоя повторную порцию отсекает inbox. Без `marker` MAX возвращает только последнее обновление, поэтому потеря сохранённого `marker` означает пропуск событий. События у MAX хранятся ограниченное время, поэтому восстановление после долгого простоя не гарантируем. [GET /updates](https://dev.max.ru/docs-api/methods/GET/updates).
- **Backend consumer:** в одной транзакции фиксирует `processed_events`, доменные изменения, аудит и outbox. ACK отправляет после коммита. Дедупликация — по `(consumer_name, event_id)`.
- **Fetcher:** объект в карантине пишется под детерминированным ключом операции, поэтому повтор задания перезаписывает тот же объект. Регистрация объекта и задача media — одна транзакция; ACK после коммита.
- **Media/CV:** ACK исходной задачи отправляет после подтверждённой брокером публикации результата. БД этим workers не нужна. При сбое вычисление может повториться: используем устойчивый ID результата для операции и детерминированные ключи объектов, повторный бизнес-эффект блокирует Backend.
- **Dispatcher:** помечает событие отправленным после publisher confirm и проверки маршрутизации (`mandatory`/обработка возврата). Если упал между отправкой и отметкой, повторяет то же событие.

Настраиваем durable-очереди, persistent-сообщения, manual ACK и ограниченный prefetch; для CV начинаем с одного задания на процесс. Publisher confirm подтверждает приём брокером, а не коммит у конечного consumer. [Гарантии RabbitMQ](https://www.rabbitmq.com/docs/confirms).

## 3. Повторы и DLQ

Временные ошибки повторяем с ограничением числа попыток, задержкой и jitter. Retry-очереди настраиваем через TTL/DLX; DLQ и маршруты объявляем явно. При перепубликации в retry/DLQ из приложения ждём confirm до ACK исходного сообщения. Ограничения надёжности брокерного dead-lettering проверяем для выбранного типа очередей: сам факт наличия DLX не даёт безусловной гарантии сохранности. [RabbitMQ DLX](https://www.rabbitmq.com/docs/dlx).

| Ситуация | Действие |
| --- | --- |
| Сбой worker до ACK | Повторная доставка |
| PostgreSQL, MinIO или брокер временно недоступны | Ограниченные повторы; не подтверждать незавершённую операцию |
| Ссылка на вложение истекла или недоступна после повторов | Постоянная ошибка; пользователь получает просьбу отправить фото заново |
| Повреждённый или запрещённый файл | Результат отклонения; повтор декодирования не нужен |
| Неверная схема или исчерпаны повторы | DLQ, диагностическая запись и ручной разбор |
| Модель не загрузилась | CV не ready и не принимает задания |
| Повторный/устаревший результат | Backend пропускает эффект и подтверждает сообщение |
| Таймаут отправки поста | `publication_unknown`; сверка перед повтором |

DLQ содержит причину и идентификаторы операции. Повторный запуск выполняем через контролируемую команду после устранения причины. На одном хосте Compose не обещаем высокую доступность или сохранность при потере диска: нужны volumes и резервные копии.

## 4. Интеграция с MAX

В S1-04 проверены возможности MAX: polling, текст, фото/файл, скачивание,
публикация, чтение, callback и удаление. Интеграцию Backend с MAX строим
через `maxapi`; эмулятор воспроизводит используемые SDK HTTP-контракты.
Протокол — [results/max-check.md](results/max-check.md),
Обезличенные примеры ответов — в [fixtures MAX](../packages/contracts/max/README.md).

Базовые факты сверены с документацией 21 октября 2026; наблюдения S1-04 добавлены
24 октября. Публикация, чтение и удаление проверены при административных правах
`write`, `read_all_messages`, `delete`. Поведение при отсутствии прав не проверено.

| Возможность | Подтверждённый контракт и решение |
| --- | --- |
| Polling | `GET /updates` предназначен для разработки/тестов и работает без активной webhook-подписки. MAX рекомендует webhook на всех этапах и запрещает polling в production; для учебного демо polling выбран осознанно, чтобы не требовался публичный домен. [Документация](https://dev.max.ru/docs-api/methods/GET/updates) |
| Webhook | `POST /subscriptions`, HTTPS:443, доверенный сертификат, ответ `200` за 30 секунд; при заданном `secret` приходит `X-Max-Bot-Api-Secret`. У нас `200` — после коммита inbox. [Документация](https://dev.max.ru/docs-api/methods/POST/subscriptions) |
| Загрузка фото | `POST /uploads?type=image` → загрузка файла по возвращённому URL → `POST /messages` с полученным token. `attachment.not.ready` допускает отложенный повтор с растущим интервалом. Изображение — до 50 МБ и не более 7680×7680 px; форматы JPG, PNG, GIF, TIFF, BMP, HEIC. [Загрузка](https://dev.max.ru/docs-api/methods/POST/uploads) |
| Отправка | Не более двух сообщений/с в один диалог, чат или канал. Ограничение общее для отправителей нашего приложения, включая уведомления в тот же адрес; соблюдаем общим счётчиком в Redis ([security.md](security.md) §2). [Отправка](https://dev.max.ru/docs-api/methods/POST/messages) |
| Удаление | `DELETE /messages?message_id=…`; нужны администраторские права и право удаления. В S1-04 первичное и повторное удаление одного ID дали `success=true`, GET по удалённому ID — `messages: []`. Проверять тело, одного HTTP 200 недостаточно. Документирован лимит два удаления/с на чат/канал. [Удаление](https://dev.max.ru/docs-api/methods/DELETE/messages) |
| Кнопки | Фото с `inline_keyboard` опубликовано в канале. Получен `message_callback`: ID в `callback.callback_id`, пользователь в `callback.user.user_id`, payload в `callback.payload`, пост в `message.body.mid`, канал в `message.recipient.chat_id`. ACK через `POST /answers?callback_id=…` дал `success=true`. Собственное голосование требует согласования. [Клавиатура](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard) |
| Статистика и реакции | В S1-04 после установки, замены и снятия реакции в `GET /messages` был только `stat.views`, без реакции; отдельного события реакции в polling не получено. Источник нативного рейтинга не подтверждён, отсутствие другого API не доказано. В документации `Message.stat` описаны просмотры и репосты. [Message](https://dev.max.ru/docs-api/objects/Message) |
| Скачивание вложений | В S1-04 URL фото и файла скачаны без токена: HTTP 200. Одна ссылка на фото оставалась доступна через 3 ч 47 мин 7 с после записи; гарантированный TTL неизвестен. URL считаем чувствительным. Истёкшая ссылка обрабатывается как постоянная ошибка (§3); токен есть только у Backend-процессов |
| Фактический формат | Входящее фото скачано как WEBP, PNG как файл — с MIME `application/octet-stream`; наш PNG, опубликованный как фото, скачан как JPEG. Проверять сигнатуру и лимиты, не доверять MIME/расширению. Поддержку WEBP или явное отклонение согласуют Dev2 и Dev4 |
| Необязательные поля | `sender` отсутствовал у входящего поста канала. Пересылка содержит `link.chat_id` и `link.message`. Inbox не должен требовать автора для любого сообщения или считать timestamp универсальным ID |

Документация сейчас указывает `https://platform-api2.max.ru`; base URL держим в конфигурации. Авторизация — заголовок `Authorization`, проверку TLS не отключаем. [Текущие указания MAX](https://dev.max.ru/docs-api/methods/POST/messages).

Эмулятор разрабатывает Dev1; MAX-адаптер и внутреннюю логику бота — Dev2. Эмулятор создаёт тестовые входящие события и сохраняет отправленные Backend ответы, но не определяет содержание ответов и не меняет бизнес-состояние заявок. Контракт согласуют Dev1 и Dev2. Эмулятор реализует только используемые методы (`updates`, `uploads`, `messages`, удаление, callback). Его ответы сверяются контрактными тестами с ответами, записанными в тестовом канале, — иначе сценарий, прошедший на эмуляторе, может сломаться на реальном MAX.

Перед внешней отправкой publisher фиксирует попытку в PostgreSQL и захватывает операцию так, чтобы её не исполняли два процесса. Повторная доставка не запускает уже завершённую операцию. Если процесс упал после начала запроса, незавершённую попытку считаем неопределённой, пока не доказан исход.

`operation_id` — внутреннее поле: не предполагаем поддержку idempotency key со стороны MAX. При таймауте, неоднозначном ответе или падении после отправки ставим `publication_unknown`. Сверка использует сохранённый ID сообщения или доступные сообщения канала, только если пост можно однозначно сопоставить; иначе нужен ручной разбор. Список сообщений (`GET /messages`) доступен боту только с правами администратора. [Работа с каналом](https://dev.max.ru/docs-api/use-cases/bot-in-chats-and-channels).

Гарантия системы: доставка с возможными повторами и идемпотентные внутренние переходы. Exactly-once для внешнего MAX API не обещаем. Неопределённые удаления и уведомления также сохраняем явно; успешный исход не выдумываем.
