# План спринтов

План начинается с текущего состояния проекта. Выполненная работа остаётся в своём спринте с автором и результатом; интеграция и расширение оформляются отдельными задачами. Каждый следующий результат расширяет уже работающую систему.

- **Порядок:** запускаемая основа → полный путь с ручной модерацией → MVP с автоматической модерацией → завершение продукта и подготовка к эксплуатации.
- **Сроки:** перед стартом команда оценивает оставшиеся задачи и доступное время участников. Номер спринта задаёт порядок результатов, но не обещает, что любой объём поместится в две недели. При необходимости этап делится на дополнительные спринты с отдельным демо.
- **Зависимости:** контракт согласуется до реализации взаимодействующих компонентов. Компонент принимается на собственных тестах; сквозной результат — отдельной интеграционной задачей.
- **Столбец зависимостей:** показывает, что нужно для приёмки результата. Проектирование, сборка образа и тесты на согласованных примерах могут начинаться раньше полной интеграции.
- **Защита вместе с функцией:** согласие появляется при приёме фото; доступ — при появлении API панели; очистка и изоляция — до превью и публикации; учёт неопределённого исхода — при первой публикации.
- **Тесты:** владелец компонента пишет его тесты и предоставляет команду запуска. Dev1 подключает их к CI; Dev4 проверяет негативные сценарии. Пропуск отсутствующей сборки не считается проверкой приложения.
- **Детализация:** спринты 1–3 описывают путь к MVP. Спринты 4–6 уточняются по измерениям и оставшимся требованиям постановки.

Роли — по [team.md](team.md): Dev1 — Илья (DevSecOps / SRE и эмулятор), Dev2 — Макс (Backend и жизненный цикл заявки), Dev3 — Роман (media, CV и правила модерации), Dev4 — Даниил (Frontend, датасеты и AppSec).

## Спринт 3. MVP с автоматической модерацией

## После MVP: продукт и ограниченная эксплуатация

После MVP завершаются оставшиеся функциональные требования постановки и проверяется готовность системы к использованию. Цель — воспроизводимый выпуск на одном стенде с известными ресурсами, нагрузкой, ответственными и способом восстановления. Наличие сервера или дашборда само по себе не означает готовность к production.

Рейтинг, розыгрыш и пересмотр решений нужны к сдаче по [assignment.md](assignment.md), хотя не входят в минимальный автоматизированный сценарий. Реальный MAX — цель интеграции при наличии доступа; эмулятор допустим по постановке, источник голосов согласуется отдельно. Kubernetes, кластеризация и автоматический CD не добавляются без подтверждённой потребности.

## Закрытие спринта

- Команда показывает заявленный сценарий на зафиксированной версии и сохраняет результаты проверок.
- Выполненные задачи сохраняют автора, ID и подтверждение. Компонентная готовность и интеграционная приёмка отмечаются отдельно.
- Незакрытая задача переносится с причиной; новый объём не добавляется в выполненную задачу задним числом.
- Изменённые контракты, роли и архитектурные решения обновляются вместе с реализацией.
