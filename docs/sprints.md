# План спринтов

Продукт растёт постепенно: каждый спринт заканчивается демо наставнику на работающей системе, и каждый следующий расширяет то, что уже работает.

- **Вертикальные срезы.** Функция появляется целиком: код, тест и проверка безопасности в одном спринте. Безопасность и тесты не откладываем на конец (Shift-Left).
- **Длина спринта** — по договорённости команды, например две недели. Незакрытая задача переносится в следующий спринт явно, с причиной.
- **Надёжность и безопасность** вводим вместе со сценарием: outbox и inbox — со спринтов 1–2, контроль доступа — со спринта 3. Спринты 4–6 расширяют и проверяют их, а не вводят впервые.
- **Детализация.** Спринты 1–3 расписаны подробно, 4–6 — крупно: их уточняем по итогам MVP.

Роли — по [team.md](team.md): Dev1 — Илья (DevSecOps), Dev2 — Макс (Backend), Dev3 — Роман (CV), Dev4 — Даниил (Frontend + AppSec).

## Спринт 1. Минимальный запуск

**Цель:** проект запускается одной командой, первая функция работает от бота до панели, команда договорилась о контрактах.

**Демо:** `docker compose up` на чистой машине → в эмуляторе написать боту `/start`, бот присылает приветствие → отправить фото, бот отвечает «Заявка №… принята» → заявка видна в списке на панели. PR без зелёного CI смёржить нельзя.

**S1-04, прогон выполнен, готово к ревью:** на реальном боте проверены polling,

и подтверждение блокировки merge при ошибке. Инструкция — в
[CONTRIBUTING.md](../CONTRIBUTING.md#проверки-ci).

## Спринт 2. Минимальное окружение

**Цель:** вся инфраструктура в Compose, и фото проходит весь путь через очереди — пока на заглушках.

**Демо:** фото в эмуляторе → оригинал в `quarantine/` → заглушка media копирует его в `sanitized/` → заглушка CV выносит вердикт → пост в канале эмулятора и уведомление автору. В панели видна история статусов заявки. Если остановить worker и запустить снова, заявка дойдёт до конца.

| ID | Задача | Кто | Готово, когда |
| --- | --- | --- | --- |
| S2-01 | Compose: RabbitMQ с очередями, retry и DLQ по схемам событий; MinIO с `quarantine/`, `sanitized/` и раздельными доступами; Redis; сети `app` и `processing` с `internal: true`; healthchecks | Dev1 | Стенд поднимается одной командой; проверено, что media и CV не видят PostgreSQL и интернет |
| S2-02 | CI: интеграционные тесты с PostgreSQL, RabbitMQ и MinIO; сборка всех образов; SAST и проверка зависимостей | Dev1 | Интеграционные тесты и SAST идут на каждый PR |
| S2-03 | Outbox, dispatcher, consumer, `processed_events`; ответы бота переведены на notifier через outbox | Dev2 | Перезапуск dispatcher или consumer не теряет и не дублирует события (тест) |
| S2-04 | Fetcher: скачивание вложения из эмулятора в `quarantine/` с лимитом размера, без декодирования, с SHA-256 | Dev2 | Объект и хеш регистрируются в PostgreSQL одной транзакцией с задачей media |
| S2-05 | Publisher и notifier в mock-режиме: загрузка фото и отправка постов и уведомлений через MAX-адаптер | Dev2 | Одобренное фото появляется в канале эмулятора; повтор задачи не создаёт второй пост |
| S2-06 | API карточки заявки с историей статусов по OpenAPI | Dev2 | Панель получает историю из API |

| S2-11 | Security-тесты fetcher: превышение размера, неразрешённый хост, редирект на внутренний адрес; модель угроз v1 по реальному потоку | Dev4 | Тесты в CI; модель угроз описывает потоки спринта 2 |

## Спринт 4. Надёжность и безопасность

**Демо:** во время показа останавливаем RabbitMQ и worker, имитируем таймаут MAX — заявки восстанавливаются, дублей нет. Отмена одобрения удаляет пост. Превышение лимита отправок срабатывает. Метрики видны на дашборде.

| ID | Задача | Кто | Готово, когда |
| --- | --- | --- | --- |
| S4-01 | Повторы с backoff, DLQ и команда контролируемого перезапуска из DLQ | Dev2 | Сообщение с неверной схемой уходит в DLQ и перезапускается после исправления |
| S4-02 | `publication_unknown` и сверка; отмена одобрения и удаление поста (`removal_*`) по [data-model.md](data-model.md) §3 | Dev2 | Переходы покрыты тестами, включая отмену во время отправки |
| S4-03 | Rate limiting в Redis: вход по пользователю, исход по чату и каналу | Dev2 | Пользователь получает понятный ответ; лимит MAX не нарушается |
