## Что работает

1. Чистый Compose запускает PostgreSQL, RabbitMQ, миграции, эмулятор,
   intake, dispatcher/notifier, HTTP API и панель.
2. Фото без согласия сохраняется как awaiting_consent. Правила отправляются
   через outbox/RabbitMQ. Согласие после подтверждённой отправки правил
   переводит заявку в validating, добавляет версию и аудит.
3. После перезапуска и повтора входных событий заявка, согласие, аудит
   и уведомление не дублируются. Том БД переживает замену контейнера.
4. Панель входит через отдельный аккаунт, читает реальные заявки,
   показывает согласие/историю, фильтрует список и восстанавливает сессию.
   После выхода серверная сессия недействительна.
5. Неавторизованные запросы и logout без CSRF отклоняются. MAX-ID, токены
   и вложения в API не выдаются. Все API-ответы no-store.

Скачивание, media/CV, публикация и реальные MAX polling/webhook не входят
в этот сценарий; validating не означает выполненную проверку изображения.

## Воспроизведение

```bash
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run ty check
# BACKEND_TEST_DATABASE_URL — локальная тестовая PostgreSQL, не production.
uv run pytest
python infra/scripts/smoke_compose.py --sprint-one --browser
```

Без BACKEND_TEST_DATABASE_URL SQL-тесты пропускаются; это не полная проверка.
Compose smoke не использует пользовательский .env, генерирует отдельные
пароли/порты и удаляет только свой проект. В CI тот же сценарий исполняется
в job Compose smoke, артефакты загружаются штатным upload-artifact.
