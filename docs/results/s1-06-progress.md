# S1-06: техническая реализация Dev2, ожидает ревью

13 ноября 2026. Mock-сценарий критериев S1-06 реализован и проверен.
Задача не объявляется закрытой: решения S1-07 и изменения кода требуют
командного ревью. Отсутствие ответов коллег не считается одобрением.

| Критерий S1-06 | Реализация |
| --- | --- |
| MAX-адаптер и /start | maxapi + эмулятор, приветствие и предъявление явно заданных правил |
| Миграции | 0001 inbox/cursor, 0002 пользователи, кампании, правила, согласия, заявки, аудит |
| Согласие | Пользователь, кампания, версия правил, время UTC, ссылка на входное событие; проверяется подтверждённая доставка правил |
| Фото без согласия | Одна заявка awaiting_consent, версия 1, UUID в ответе |
| Согласие после фото | Ожидающие заявки пользователя в кампании получают validating, ссылку на согласие, новую версию и аудит |
| Фото после согласия | Новая заявка сразу validating, версия 1 |
| Повтор события | Уникальный inbox; бизнес-обработка только новой строки, заявка/согласие/аудит/ответ не дублируются |
| Продвижение marker | Inbox, бизнес-изменения, аудит, ответ и marker коммитятся вместе; при ошибке всё откатывается |
| Файл не скачивается | Сохраняется только признак фото; URL/токен вложения не сохраняется, media/CV не запускаются |

Настройка кампании обязательна для приёма заявок: административная команда
manage.py сохраняет явно переданные версию и текст правил, выводит UUID для
BACKEND_CAMPAIGN_ID. Без него run_inbox_bot.py остаётся проверкой связи.
Старый run_bot.py не использует БД. [Инструкция](../../apps/backend/README.md).

Рабочие допущения до принятия S1-07:

- Согласие действует на пользователя, кампанию и версию правил. Заявка
  хранит ссылку на конкретное согласие. Идентичность синтетического автора
  дополнительно разделена по source_id, чтобы сброс эмулятора не переносил
  согласия на заново созданных тестовых пользователей.
- /agree ВЕРСИЯ проверяет текущую версию. Сокращённый /agree возможен после
  подтверждённой доставки текущих правил. Недоставленные/неопределённые
  правила не дают основание для согласия. Фото с подписью /agree не даёт согласие.
- Новое согласие продвигает все ожидающие заявки этого пользователя в кампании.
  При смене правил новые фото требуют новое согласие; старые заявки сохраняют
  прежнюю ссылку. Текст существующей версии правил административная команда
  менять запрещает, добавляется новая версия.
- Одна заявка создаётся на одно событие с фото, повторное отдельное сообщение
  с тем же файлом пока не считается файловым дублем. SHA-256 появится в S2-03.

Проверки: 44 теста на PostgreSQL 18 и localhost-эмуляторе. Проверены миграции
вверх/вниз и соответствие моделей, откат порции вместе с бизнес-эффектами,
повторы и перезапуск, порядок фото/согласия, недоставленные правила,
смена версий, изоляция пользователей/кампаний, аудит, неизвестная отправка.
Также выполнено отдельное CLI-демо: миграции, настройка кампании, фото,
согласие, перезапуск процесса, второе фото. Результат: две заявки validating,
одно согласие, три записи аудита, три ответа без повторной обработки истории.

Не входит в эту реализацию: реальные MAX polling/webhook, скачивание,
media/CV, публикация, панель и аккаунты. Ответ хранится в inbox, не в готовом
RabbitMQ/outbox-конвейере: S1-17 и S1-18 остаются отдельными задачами.
Sending после аварии и unknown не отправляются автоматически; пока требуется
ручная сверка. Синтетические demo-rules.txt не являются условиями реального
сервиса. Локальный mock-режим не предназначен для production.
