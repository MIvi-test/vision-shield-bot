# Оценка серверных ресурсов vision-shield-bot

16 ноября 2026 · предварительная оценка для полного конвейера фотомодерации в MAX.
## Рекомендуемая конфигурация

**Для первого полного стенда: 4 гарантированных vCPU, 16 ГиБ RAM, без GPU. Диск — от 100 ГБ доступного SSD/NVMe с возможностью расширения; для 30-дневного сценария по 1000 фото/сутки размером 2 МиБ — 200 ГБ (§5).**

На одной машине размещаются Backend и его фоновые процессы, PostgreSQL, RabbitMQ, Redis, MinIO, media/CV, панель и компактный мониторинг. Начальная параллельность — одно изображение в CV и одно в media; всплески обрабатываются через очередь. Обновление CV — с остановкой старого процесса перед запуском нового.

Это конфигурация для проверки, а не измеренный минимум. **Очищенные фото хранятся, пока заявка активна или опубликована; диск рассчитывается по накопленному объёму (§5).** CI-сборки и резервные копии размещаются вне этой ноды; высокая доступность в расчёт не входит.

## 1. Расчётная нагрузка

| Параметр | Принято для расчёта |
| --- | --- |
| Новые фото в сутки | 60, 80, 250, 500 и 1000 |
| Проверка всплеска | Одновременное поступление 1000 фото |
| Бюджет обработки пачки | 4 часа, то есть не менее 250 фото/час по полному пути |
| Входное изображение | Обычно 2 МиБ; предел профиля — 10 МиБ и 25 Мп |
| Очищенное изображение | Расчётно 0,5 МиБ; дополнительный сценарий — 2 МиБ |

1000 фото/сутки — выбранная нагрузочная цель, а не прогноз по числу подписчиков. Фактический спрос и нагрузка от команд, голосов и уведомлений пока не измерены. Четыре часа — допущение для времени обработки пачки, не срок хранения фото и не утверждённый SLA.

## 2. Поправка по PR №22

В S1-09 выбраны OpenCLIP ViT-B/32 LAION-2B для темы и Falconsai ViT для NSFW. Замер выполнен на i3-1215U, Windows 11, Python 3.13, с шестью потоками PyTorch: 77 подготовленных изображений, каждая модель в отдельном процессе.

| Модель | Веса | Пик RAM | p50 / p95 на фото |
| --- | ---: | ---: | ---: |
| OpenCLIP ViT-B/32 LAION-2B | 605 МБ | 1,57 ГБ | 106 / 122 мс |
| Falconsai ViT NSFW | 343 МБ | 0,80 ГБ | 253 / 309 мс |

Единицы размеров приведены как в отчёте PR. Сумма p50 — около 0,36 с, сумма p95 — 0,43 с; это **не измеренные перцентили общего worker**. Суммарная загрузка из локального кэша — около 21 с.

## 3. CPU и время обработки

До замера CPU time сохраняется условный бюджет **3,6 CPU-с на фото**: media — 0,5; CV — 3; прочая обработка — 0,1. Это расчётное допущение; длительность инференса из PR не равна расходу CPU.

Для оценки очереди принят отдельный сценарий: CV обрабатывает фото за 3 с, полезная загрузка слота — 60%. Получаем `0,6 / 3 × 3600 = 720 фото/час`.

| Фото/сутки | CPU-часов/сутки при 3,6 CPU-с/фото | Время CV для всей пачки при 720 фото/час |
| ---------: | ---------------------------------: | ---------------------------------------: |
|         60 |                               0,06 |                                    5 мин |
|         80 |                               0,08 |                               6 мин 40 с |
|        250 |                               0,25 |                              20 мин 50 с |
|        500 |                               0,50 |                              41 мин 40 с |
|       1000 |                               1,00 |                          1 ч 23 мин 20 с |

Для 1000 фото за 4 часа средняя вычислительная потребность с запасом:
`1000 × 3,6 / (4 × 3600 × 0,6) ≈ 0,42 CPU`.
С резервом 2 CPU для инфраструктуры расчёт округляется до 3 CPU; **выбираем 4 vCPU** для совместной работы сервисов. Начальный замер CV — с двумя потоками PyTorch.

Таблица показывает только расчётное время CV. Скачивание, media, ручная проверка, публикация и повторы увеличивают полную задержку. Поэтому ориентир «10 минут на 1000 фото», полученный из суммы p50 в PR, не используется как обещание производительности.

## 4. RAM

Плановые бюджеты для одного CV-процесса и одного media-слота:

| Компонент | Пиковый бюджет, ГиБ |
| --- | ---: |
| ОС и контейнерный runtime | 1,00 |
| Backend и фоновые процессы | 1,00 |
| PostgreSQL | 1,50 |
| RabbitMQ | 0,50 |
| Redis | 0,25 |
| MinIO | 0,50 |
| Proxy, статика панели, компактный мониторинг | 0,25 |
| CV: две модели в одном процессе | 3,00 |
| Media: родитель и декодер до 512 МиБ | 0,625 |
| I/O-буферы | 0,25 |
| Файловый кеш | 2,00 |
| **Итого** | **10,875** |

С 20% свободной памяти: `10,875 / 0,8 ≈ 13,6 ГиБ` → **16 ГиБ RAM**.
Это распределение бюджета, а не замер сервисов. Особенно нужно проверить общий расход фоновых процессов и мониторинга. Две одновременно загруженные копии CV при обновлении в этот вариант не заложены.

## 5. Диск и хранение

Для расчёта принимаем политику хранения из [security.md §3](../security.md#3-персональные-данные-и-privacy):

- оригиналы удаляются после обработки и окна повторов;
- очищенные фото хранятся, пока заявка активна или опубликована; после отказа или удаления поста — короткий срок, затем удаление;
- отзыв согласия и запрос на удаление данных обрабатываются по тому же разделу `security.md`.

Численная длительность короткого срока и окна повторов пока не определена. Опубликованные фото не удаляются автоматически через 4 часа или 30 дней. В `security.md` эта политика обозначена как предложение, которое команда утверждает до демо с реальными данными.

Расчётные допущения: резерв оригиналов на одну пачку из 1000 файлов; БД, индексы, аудит и логи — условно 0,025 МиБ на поступившее фото; 30% диска остаются свободными, резервные копии хранятся отдельно. Для таблицы ниже служебные записи посчитаны за 30 дней — это горизонт оценки, не TTL: аудит по `security.md` сохраняется до конца проекта, логи ротируются отдельно.

| Статья | Бюджет, ГиБ |
| --- | ---: |
| ОС и runtime | 10 |
| Образы, включая предыдущую версию | 15 |
| Веса, включая копию при обновлении | 5 |
| WAL, очереди, метрики и временные файлы | 10 |
| **Служебный объём** | **40** |

Формула для 1000 фото/сутки на 30-дневном горизонте, где `S_in` и `S_out` заданы в МиБ, а `K` — число одновременно хранимых очищенных фото (активные, опубликованные и ожидающие удаления после отказа/удаления поста):

`Диск, ГиБ = (40 + (1000 × S_in + K × S_out + 1000 × 30 × 0,025) / 1024) / 0,7`.

| Хранимых очищенных фото | Размер входного / очищенного фото | Требуется с запасом |
| ---: | --- | ---: |
| 1000 | 2 / 0,5 МиБ | 61,7 ГиБ ≈ 66,2 ГБ |
| 1000 | 10 / 2 МиБ | 74,9 ГиБ ≈ 80,5 ГБ |
| 30 000 | 2 / 0,5 МиБ | 81,9 ГиБ ≈ 87,9 ГБ |
| 30 000 | 10 / 2 МиБ | 155,8 ГиБ ≈ 167,3 ГБ |

Первые две строки показывают запас для 1000 хранимых фото, а не ёмкость на весь жизненный цикл. 30 000 фото — сценарий поступления 1000 в сутки в течение 30 дней с сохранением всех очищенных изображений. **При очищенном фото 2 МиБ на этот горизонт выбираем диск 200 ГБ.** 100 ГБ подходят для стартового стенда или меньшего накопленного объёма; опубликованные изображения продолжают занимать место после этого горизонта.

Размер очищенного JPEG в байтах пока не ограничен профилем; 2 МиБ — проверочный сценарий, а не гарантированный максимум. Без срока окончания публикаций или предела накопленного объёма фиксированная ёмкость не покрывает весь жизненный цикл: нужны контроль свободного места и расширение диска. Оригиналы при задержках обработки/повторов также могут превысить одну пачку. Служебные данные требуют ротации и очистки старых образов; бюджет БД и аудита пересчитывается на фактическую длительность проекта.
