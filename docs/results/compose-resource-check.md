# Проверка ресурсных ограничений mock-стенда

## Вывод

Текущий mock-стенд не упирается в RAM или PID и успешно разбирает
пачку из 1000 фото-событий. CPU-квота бота ограничивает пиковое выполнение,
но её удвоение дало лишь небольшое ускорение полного пути в одном прогоне.
Оснований срочно повышать лимиты по этому эксперименту нет.

Это проверка текущего приёма заявок, а не полного проекта: файлы не
скачиваются, media/CV, API панели и доставка RabbitMQ ещё не работают.

## Условия

- Текущий Compose из рабочего дерева, не зафиксированный релиз.
  Эмулятор уже имеет 0,5 CPU; прежнее значение 0,25 в таблице плана исправлено.
- Docker видит 16 логических CPU и 16 446 107 648 байт RAM (около 15,3 ГиБ),
  cgroup v2. Это локальная машина, а не целевая нода с 4 vCPU.
- Отдельный проект `vision-shield-loadcheck`, отдельные пустые тома,
  синтетическая кампания и пользователь. Рабочий `.env` не менялся.
- До нагрузки получены правила и подтверждено согласие. На прогон —
  1000 событий `photo=true` с уникальной синтетической подписью,
  восемь параллельных запросов в служебный API эмулятора.
- 30 секунд фонового режима, пачка, 10 секунд восстановления.
  Liveness HTTP опрашивался примерно 5 раз/с; cgroups — раз в 3 секунды.
  Фоновый режим включает эти пробы и штатные healthchecks.
- Для сравнения квота только тестового бота изменена через `docker update`
  с 0,5 до 1 CPU. Вторая пачка выполнена на том же прогретом стенде;
  рабочий Compose не менялся. По одному прогону каждой конфигурации:
  различия не являются статистически подтверждённой оценкой ускорения.

Сводные результаты приведены ниже. Исходный JSON замера не включён в репозиторий.

## Скорость и задержки

| Показатель | Бот 0,5 CPU | Бот 1 CPU, только эксперимент |
| --- | ---: | ---: |
| Отправка 1000 событий в эмулятор | 1,17 с | 1,37 с |
| От начала отправки до наблюдения всех 1000 ответов | 14,16 с | 13,40 с |
| От входного события до ответа, p50 | 7,06 с | 6,41 с |
| От входного события до ответа, p95 | 12,45 с | 11,25 с |
| Максимальная задержка ответа | 12,92 с | 11,75 с |
| HTTP liveness p95 во время пачки | 3,27 мс | 2,38 мс |
| Среднее потребление CPU бота во время пачки | 0,447 ядра | 0,505 ядра |
| Периоды CPU с throttling у бота | 78 из 142 | 1 из 134 |

Задержки ответов включают ожидание остальных событий в пачке; это не
длительность одной SQL-операции. Время обработки вычислено по timestamp
входного события и соответствующего исходящего ответа, сопоставленных
через UUID заявки. Полное завершение наблюдалось опросом раз в 0,5 секунды.

В обоих прогонах созданы ровно 1000 новых заявок и отправлены 1000 ответов.
Нет ошибок запросов/проб и записей `pending`, `sending`, `unknown` после пачки.
Доставка через RabbitMQ этим не проверялась: брокер оставался без заданий.

## Память и процессы

Максимум `memory.peak` за жизнь контейнера, включая запуск и оба прогона:

| Сервис | Пик памяти, МиБ | Лимит, МиБ | PID в снимках после пачек / лимит |
| --- | ---: | ---: | ---: |
| PostgreSQL | 94,1 | 1536 | 12 / 256 |
| RabbitMQ | 196,6 | 512 | 17–28 / 256 |
| HTTP Backend | 59,8 | 384 | 4 / 128 |
| Бот | 90,8 | 384 | 5–6 / 128 |
| MAX-эмулятор | 69,3 | 256 | 4 / 128 |

Значения PID — снимки, не максимум за всё время. Превышений `pids.max`,
событий достижения `memory.max` и OOM-kill за измеренные интервалы не было.
RabbitMQ после первой пачки не сообщил локальных memory/disk alarms.
Память эмулятора растёт с историей в памяти: две пачки не проверяют
многодневное накопление или ограничение длины журнала.

Использована память cgroup, включая учитываемые ядром страницы и кеш.
Это отличается от Linux `docker stats`, который вычитает неактивный
файловый кеш; [описание Docker](https://docs.docker.com/reference/cli/docker/container/stats/).

## Что означает throttling

При 0,5 CPU бот использовал в среднем около 89% своей квоты во время
пачки, а в 78 периодах исчерпывал доступное CPU-время. Удвоение квоты почти
устранило throttling, но время разбора уменьшилось лишь примерно на 5%.
Значит, CPU-квота влияет на этот пик, однако результат не подтверждает,
что она определяет всю задержку. Для разделения ожидания БД, HTTP и работы
Python нужен дополнительный профиль; причину задержек этим тестом не выделяли.

Небольшой throttling наблюдался также у Backend, RabbitMQ и эмулятора,
в том числе в фоновом режиме: их короткие всплески/healthchecks делят
квоту с основным процессом. Это не вызвало ошибок liveness в эксперименте.
Доля throttled-периодов не равна доле потерянной производительности
или доле времени недоступности; [счётчики cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).
